# AGENTS.md

PyGPGPU runs Python functions as GPU kernels on OpenCL (default), CUDA, and HIP, and can also run them serially in the interpreter through the `python` backend. Pure Python + ctypes, Python >= 3.7, packaged with setuptools. `README.md` is the English version (shown first on GitHub); `README.zh-CN.md` holds the Chinese version and the two link to each other at the top — when editing user-facing docs, keep both in sync.

## Language policy: English only (hard rule)

- **All comments, docstrings, error messages, log/UI text, and every other string in code must be written in English. Never generate Chinese (CJK) characters** in `.py` / `.cl` / `.cu` / `.hip` sources, generated stubs and templates (`*.pyi`, `*.pyi.in`), `examples/`, or any documentation file.
- The **only** permitted Chinese files are `README.zh-CN.md` mirrors of an English `README.md`, in any directory (currently two: repo root and `examples/`). When user-facing docs change, keep the matching mirror in sync. Nothing else may be added in Chinese, and no code, script, or tool may emit Chinese text.
- One narrow exception, and do not extend it: the native-form author name in `pyproject.toml`'s `authors` table, kept alongside the ASCII `Binghui Wang` entry used everywhere else. Machine-readable packaging metadata is the only place CJK is allowed; the ASCII form is canonical for all prose, code, and display.
- If you find Chinese in a file you are touching, translate it to English as part of that edit rather than copying the style.
- Spot check before finishing a task: search the tree for CJK codepoints (`rg -n '[\p{Han}]' --glob '!README.zh-CN.md'`) — the only acceptable hits are the two `README.zh-CN.md` mirrors and the native-form author name in `pyproject.toml`. Language bars link with the word `[Chinese]`, never CJK, so no other file needs an exemption.
- This rule is self-referential: AGENTS.md itself contains no CJK, and neither should any file you add.

## Type annotation policy: name the type, and reach for `Any` last (hard rule)

- **Every annotation names the real type. `Any` is the last resort, not the default.** It is a *permission to stop checking*, so a shape the code already relies on — a dict with fixed keys, a pair the emitters pass around, a value from a closed set — must be written down.
- **`any_budget.py` enforces it, and it runs as the fourth step of `check.py`.** It counts the hand-written `Any` annotations in the tree and fails when the total crosses the recorded ceiling, so a new `Any` has to be paid for by removing an old one. It tells the two kinds apart, because they mean different things: a **dtype slot** (`np.ndarray[Any, Any]`, `np.number[Any]`) is numpy's own generic parameter — the slot accepts any dtype and writing it says exactly that, so it is not a budget item — and a **hand-written `Any`** (`Dict[str, Any]`, `Callable[[str], Any]`, a bare `-> Any`) is a shape this package could have named and did not, and that is what the budget holds. Run `python any_budget.py --list` to see every occurrence with its file and line. The ceiling is the tree's current count; raising it is a decision to argue for, not a thing to do to make a check pass.
- **A repeated shape gets a name, once.** `kernel/translator/` carries the translator's two: `DeviceType` (a scalar/vector name, a `("*", base)` pointer, an `("image", ...)` sample, or a `("shared_slice", ...)` group buffer — the closed set `is_ptr`/`is_vec`/`is_image` already accept) and `Translated` (C text plus that type, what every `_visit_*` returns). Structures with fixed keys are `TypedDict`s (`ReturnPosition`, `ReturnLayoutEntry`, `OuterVarEntry`, `HostValueEntry`), and a shape several independent classes share is a `Protocol` (`VarInfoLike` / `ArgInfoLike` / `StructInfoLike` / `KernelInfoLike` in `cparser/ts_parser.py`, one per backend by design so the walk stays backend-neutral). Add the alias next to the thing it describes, not in a separate module.
- **`object` is not a synonym for `Any`, and it is usually the better one.** `Any` disables checking on everything it flows into; `object` says "any object — narrow it before use" and a checker enforces the narrowing. A `**kwargs` or an exec namespace holding caller values is `Dict[str, object]`; a list of launch arguments is `List[object]`.
- **`Any` is almost never about a *kind* of value — it is about what a stub returns.** The candidates that look dynamic are not: `ctypes.Structure` / `ctypes.Union` / `ctypes.Array` / `_SimpleCData` are ordinary classes, a generated vector class is a `ctypes.Structure` subclass (`type[ctypes.Structure]` for the class, `ctypes.Structure` for an instance), a tree-sitter `Node` and `Parser` are ordinary classes and are annotated as such in `cparser/ts_parser/`, and this package's driver handles (`cudaTextureObject_t`, ...) are classes too. Backend-neutral code that must not import a backend names the shape with a `Protocol`, or takes `object` and switches on `type(value).__name__` — which is what `translator.TEXTURE_HANDLE_TYPES` already does.
- **Where `Any` actually enters is three stdlib stubs**, and annotating the destination stops it there: `value.__globals__` (typeshed spells it `dict[str, Any]`), `getattr(obj, name)` when `name` is computed at runtime, and `property.fget`/`fset` (`Callable[..., Any] | None`). Prefer the typed attribute over the `getattr` when the attribute has a name (`func.__globals__`, `cls.__dict__`); otherwise take it as `object` and narrow. A bare `Any` on a parameter or a return is a decision someone made, not a necessity — so write the reason beside it.
- **Never widen an annotation to make a check pass, and never narrow one to look tidy.** A new `ty` diagnostic after an annotation change is a regression to fix, not a rule to silence.
- `TypedDict` and `Protocol` live on PyGPGPU's Python 3.7 floor, so they come from `typing_extensions` (as `cparser/ts_parser/` and `kernel/decorator/` already do for `ParamSpec`); a `TYPE_CHECKING` block is where a name that only an annotation needs belongs, so the runtime import stays lazy.
- **Annotations do not change runtime behaviour, so the verification for an annotation change is the checker, not the test suite.** Run `python -m ty check` (and `python -m ruff check`); the baseline on a machine without `pygf` installed is the pre-existing `unresolved-import` set, so compare counts and kinds rather than expecting zero. Run the tests once at the end, for the behaviour the change sits next to.

## Setup and verification

- `pip install -e ".[dev]"` (dev dependencies: pytest, ruff, ty). No CI and no pre-commit hook; the feature tests live in `tests/` and run with `python -m pytest tests/ -q`. The whole-repo check is `python check.py` (runs `ruff check --fix` then `ty check` against the config in `pyproject.toml`).
- Fast checks without a GPU: `python -m compileall -q pygpgpu` and `python -c "from pygpgpu.kernel import kernel"`.
- The end-to-end smoke tests are the numbered scripts in `examples/` (each is standalone: `python examples/01_basic_kernel.py`; no backend specified means probe `cuda -> hip -> opencl`). `examples/06_handwritten_kernels.py` covers importing ONE handwritten `.cl` through `kernel_import` (single-backend case, struct parameters); `examples/15_kernel_import.py` covers the same-named three-backend case (brackets, overloads, KeyError); `examples/09_reduction.py` covers atomics, local memory and tree reductions.
- `tests/conftest.py` parameterizes every test over the `python` backend plus whichever device backends this machine has, and provides the `runner(kernel, *args)` fixture that brackets the current backend. Write a test once and it covers every backend; use the `gpu_backend` fixture for tests that need a real device.
- **A backend's runtime is initialized on a BACKGROUND thread, and its load failure is deferred to first use -- never swallowed.** Each driver module (`cuda/driver/cuda.py`, `cuda/driver/nvrtc.py`, `hip/driver/hip.py`, `opencl/driver/cl.py`) owns the same contract: `_start_init()` launches `init()` on a named thread and returns at once, `_wait_ready()` blocks on an event, and every driver call goes through `Func.__call__`, which calls `_wait_ready()` first. **Both are private and a user never calls them**: the backend package starts the thread when it is imported, and a call waits by itself. `init()` catches its own failure and records it (`MetaCUDA.last_init_error` / `MetaNVRTC` / `MetaHIP` / `MetaCL`) instead of raising: `import pygpgpu.cuda` succeeds without `nvcuda.dll`, and `kernel_import` relies on that to parse `.cu` sources on machines with no CUDA. Three things are load-bearing. (1) **The preheat inside `init()` must go through the raw DLL, not through `Func.__call__`**: init runs ON the background thread, and `Func` waits for init, so going through `Func` there would wait for itself -- a deadlock. (2) `init()` must not be called synchronously again anywhere: the thread is the only initializer (`_start_init()` is idempotent under a lock). (3) The background thread is what makes the import cheap: `cuInit` alone is ~600ms and releases the GIL, so it overlaps with the importing thread's own work; `import pygpgpu.cuda` returns in ~40ms and the wait happens at the first call. Nothing special may be added in callers to handle the recorded error -- a broken runtime fails exactly where it is used, with the driver's own OSError/RuntimeError. Do not turn `init()` back into a raising call, do not call it synchronously, and do not make `_start_init`/`_wait_ready` public.
- HIP compiles by spawning ROCm's clang (hipRTC is unusable on the tested ROCm 7.2 Windows). The executable is `clang.exe` under `<rocm root>/bin` on Windows and `clang` (or `hipcc` on `PATH`) on Linux, and the ROCm root comes from `ROCM_PATH`/`HIP_PATH` plus `/opt/rocm*` there rather than from drive letters. Set `PYGPGPU_HIP_INCLUDES` (`os.pathsep`-separated) when MSVC/Windows SDK headers are not auto-discovered; on Linux ROCm's clang finds the system headers itself, so the list is normally empty.
- **Metal is a fifth backend, and it is Metal-only: it needs macOS plus a real Apple GPU.** The driver (`metal/driver/metal.py`) follows the same background-init contract as the others (`_start_init` / `_wait_ready` / `MetaMetal.last_init_error`), so `import pygpgpu.metal` succeeds on every machine and `probe` answers "unavailable" off-Apple -- a Mac virtual machine also has no device (`MTLCreateSystemDefaultDevice` returns nil), which is why CI supplies a real Apple-Silicon runner rather than a VM. Four things are load-bearing. (1) **Code generation is OpenCL-shaped, with Metal's prologue around it.** `FunctionTranslator` carries `_opencl_syntax` (true for `opencl` and `metal`) and `_metal_syntax`: every emission site asks the first, so the shared body keeps one spelling, and only the signature (`kernel void f(...)`, `device`/`threadgroup` address spaces) and the two work-item facts are Metal's. (2) **The work-item numbers are kernel parameters, not calls.** MSL has no `get_global_id()`; the generated prelude (`kernel/metal_codegen.py`) defines those six names as macros over attribute-decorated parameters (`uint3 p [[thread_position_in_grid]]` etc.), so the body text is unchanged and `_launch_id_code` keeps returning `get_global_id(axis)`. The prologue parameters are appended by `parameter_declarations()`, which is why they are part of the signature digest and the cache key. **Each macro body is wrapped in one outer pair of parentheses, and that is load-bearing**: a conditional expression binds looser than `%`, and `_flattened_launch_id` emits `(gid % size) * stride + ...`, putting an expansion on the left of a `%` -- without the outer group the conditional would swallow the rest of the fold and the work position would be silently wrong on the device. The expansion was verified by compiling that fold with a real C compiler (an 8x4x1 grid at (7, 3, 0) folds to 31, which is what it printed), and `tests/test_metal_codegen.py` pins the parentheses structurally. (3) **The dispatch pair is CUDA's, unchanged**: `(blocks_per_grid, threads_per_block)` maps onto `dispatchThreadgroups:threadsPerThreadgroup:` one-to-one, with no `blocks_to_global` conversion -- `utils.blocks_to_global` stays OpenCL's alone. (4) **Buffers are `StorageModeShared` and copies are `memcpy`, but a scalar is not a buffer.** The read-back is whole-buffer, so a written buffer is still uploaded (the rule that matters on every backend), and `bind_data` still records a read-back destination for an argument the kernel never touches. A **scalar** parameter, however, lives in MSL's thread address space, so it binds with `setBytes:length:atIndex:` -- binding it with `setBuffer:` presents a pointer where the kernel declared a value and the pipeline rejects the launch. `_bind_args` therefore returns `(index, value, is_buffer)` and the encoder branches on that flag; `_scalar_bytes` writes the **device's** width (`const int` is 4 bytes, not python's 8), which is `_SCALAR_SIZES`' job. `tests/test_metal_launch_path.py` pins the widths per declared type and that the two paths stay distinct.
- **The Metal prelude is ONE blank-line-free block, and that is load-bearing.** A generated file's header is split on blank lines by `source_paths._split_source`, and a piece whose first line is not `#`/`struct`/`typedef struct` is classified as a function definition and dropped from the header. The prelude is `#include <metal_stdlib>` + `using namespace metal;` + the six `#define`s, so: (1) the `using` line must never start a piece of its own, or the next write loses it and every macro then names an unqualified `uint3` -- an MSL compile error; (2) the block must be byte-identical every time it is written, because `append_source` re-writes the header on each compile of a module and `_canonical_header` dedupes a mixed block by its exact text. Emitting the three parts on consecutive lines satisfies both: one piece, starting with `#`, identical on every call. Verified by compiling the same kernel four times -- the file stays byte-for-byte the same with one include, one `using` and one copy of each macro. `tests/test_metal_codegen.py` pins the no-blank-line shape and the rewrite idempotence.
- **A `.metal` module is type-checked like any other, from a table derived from OpenCL's.** `kernel_import._scalar_tables("metal")` used to return `{}`, and an empty table makes `_declaration_accepts` answer `None` for every parameter -- the wrapper reads that as "cannot tell" and lets the call through, so a wrong dtype failed on the device instead of at the call. The table is now built lazily from `CLInfo.basic_types` and `CLInfo.vec_types`, filtered to what MSL actually declares: the scalar spellings (`char`/`uchar`/`short`/`ushort`/`int`/`uint`/`long`/`ulong`/`float`/`double`) and the vector widths **2, 3 and 4 only** -- MSL has no `float8`/`float16`, unlike OpenCL. The *types* are the very ones the other backends use, because a vector is a layout of its components and does not depend on which device reads it; only the names and widths are Metal's. Two consequences are visible downstream. (1) The generated `.pyi` now annotates a parameter as `NDArray[np.float32]` where it used to fall back to `NDArray[float]`, which is what a resolved table buys. (2) A `float4*` parameter requires `float4`-typed elements, not four `float`s. `tests/test_metal_launch_path.py` pins the table's contents, the dtype refusals and the vector case. One behaviour is deliberately left alone: passing an array where a scalar is declared is accepted on **every** backend (the shared `int()`-style conversion accepts it), so Metal matches the others rather than diverging in one place.
- Metal's MSL source is read by a small declaration scanner (`metal/oop/program_parser.py`), not by tree-sitter: none of the installed grammars accepts `kernel void f(...)` (the CUDA grammar tags the `void` an ERROR node), and this package *generates* that shape itself, so a full parser would buy nothing. The scanner reads exactly what a launch binds -- entry points and their parameter names/types -- and raises on anything it cannot read rather than guessing.
- **Metal's shared memory and atomics are MSL's, not OpenCL's.** Two spellings differ and neither is cosmetic. (1) **A `zeros_per_group` buffer is `threadgroup`, not `__local`** -- `parameter_declarations()` emits `threadgroup uint* _local0` and `_metal_syntax` picks it, while the sampler parameters stay OpenCL's alone (`backend == "opencl"`, not `_opencl_syntax`, because MSL has no sampler argument). (2) **Atomics are the C++11 `atomic_fetch_*_explicit` family, never `atomicAdd`.** `emit_atomic` dispatches on `backend == "metal"` to `_emit_atomic_metal`, which casts the pointer to **the address space the buffer lives in** -- `(threadgroup atomic_uint*)` for a group scratch buffer, `(device atomic_uint*)` for an array argument -- because MSL overloads the atomics on that reference type and one address space cannot be cast to the other (the same rule OpenCL enforces with `__local`/`__global`). `atomic_cas` is `atomic_compare_exchange_weak_explicit`, which takes the expected value by pointer and answers a `bool`, so it is emitted as a small block holding that value rather than as an expression. Every operation passes `memory_order_relaxed`: the update is atomic, and a `barrier()` is what orders the group. `tests/test_metal_codegen.py` pins the per-operation spelling, the two address spaces, the CAS shape, and a real shared-memory histogram compiled through `PyKernel._compile`.
- **Buffer parameters get their address-space qualifier from one place, `_buffer_qualifier()`.** A kernel signature names many buffers -- the caller's arrays, the returned-value slots, the return claim/site words, the outer-scope arrays and the host-created ones -- and all of them need the same space. Metal writes `device `, OpenCL writes `__global `, CUDA/HIP write nothing (a plain pointer is already global). Keeping that in one method is what stopped the return slots from being spelled `__global` in an MSL source: they were four separate `_opencl_syntax` tests before. The return **claim word** is Metal's other shape: MSL's compare-and-swap answers a `bool` and takes the expected value by pointer, so the claim is a `_claim_expected = 0` local, the exchange itself, and then a read-back (`_ret_claim[0] == 1`) -- where OpenCL uses `atomic_cmpxchg(...) == 0` and CUDA `atomicCAS(&x, 0, 1) == 0`. `tests/test_metal_codegen.py` pins the slots as `device`, both foreign spellings' absence, and each backend's own claim form.
- **No packaging or lint config needed a change for Metal.** `[tool.setuptools.packages.find]` already uses `include = ["pygpgpu*"]`, so `find_packages` discovers `pygpgpu.metal`, `pygpgpu.metal.driver` and `pygpgpu.metal.oop` with no extra entry (verified: 23 packages, the three metal ones among them). The backend ships no data files of its own -- the generated MSL lives in the source-tree cache, not in the wheel -- so `[tool.setuptools.package-data]` needs nothing either. Ruff's `extend-exclude` and ty's `src.exclude` name only the vendored pcpp tree, the legacy cparser sources and generated `.pyi` stubs, so every metal module is checked like any other; both run clean on it.
- **Images are refused on Metal by the translator, exactly as HIP's are.** MSL does have texture objects (`texture2d<float, access::sample>` and `access::write`), so this is a missing implementation rather than a missing capability -- but the whole image path is Metal's own: the parameter type, the sampling call with its sampler state, the store, and the host-side `MTLTexture` binding all differ from the OpenCL formulation this backend reuses. Without them the generated source carries `__read_only image2d_t`, which MSL has no notion of, so `_reject_metal_image` refuses reads and writes with a message naming the backends that work. The check is `self._metal_syntax`, not `launch_backend`, because Metal is not HIP's reuse case -- it has its own code generation -- and it runs before `_reject_hip_image` so a Metal kernel reports its own reason. `tests/test_metal_codegen.py` pins both directions and confirms OpenCL/CUDA are unaffected.
- **A Metal kernel launches asynchronously through a completion poller.** `submit`/`async_call` used to raise `NotImplementedError`; they now work, without Objective-C blocks. The launch encodes and commits (`BoundKernel._enqueue`), and a poller thread reads the command buffer's `status` until it reaches `MTLCommandBufferStatusCompleted` (3), then reads `error`, runs the copy-backs, and settles the future (`settle_future`, so a bare `await` wakes). Three facts are load-bearing. (1) **The bracket reaches the async launch**: `submit`/`async_call` go through `__getitem__(None)` -> `BoundKernel._launch_async`, and the decorator's async path brackets `phase_geometry` before calling them -- the automatic grid here is ONE threadgroup of ONE thread, so an unbracketed bracketed-shape kernel would silently visit one work item. (2) **The claim serial travels with the launch**: `_claim_entries` captures each buffer's serial at claim time and the release validates it (`Buffer.unuse(claim_serial)`), because the poller releases from another thread while the caller's next launch may have claimed the same pooled buffer. (3) **Per-launch bound entries**: `take_bound_entries()` consumes the list rather than leaving it on the kernel, so two in-flight launches of one kernel do not overwrite each other's copy-backs. The synchronous path is unchanged (`waitUntilCompleted` + inline `_finish_buffer`). Separately, `Device.vendor` answers `"Apple"`: the shared `_device_match_keys` reads `vendor` with a `getattr` fallback, so it *could* be absent, but then a selector like `metal:apple` would silently match nothing. `tests/test_metal_launch_path.py` pins the dispatch-shape plumbing and the vendor.

- **A complex scalar parameter is bound like a scalar, because MSL has no complex type.** `kernel/complex.py` declares the two fixed records (`c64` is a `float` pair, `c128` a `double` pair), and the translator emits one as a parameter the way it emits a scalar: **by value**, in MSL's thread address space (`c64 value`), so it binds with `setBytes:length:atIndex:` and never takes the buffer path. Three things had to follow. (1) `program_info.COMPLEX_TYPE_NAMES` is the closed set the parser can read back, and `ArgInfo.check_type` accepts a python `complex` or a numpy complex scalar for exactly those names -- without the branch the integer fallback refused a `c64` parameter with "must be an integer", which names neither the type nor what it accepts. (2) `_scalar_bytes` writes the **record's** bytes: two components in declaration order (`re`, `im`, which is numpy's own complex layout), each through the range check a `float`/`double` parameter gets -- so a `c64` refuses a value float32 cannot carry with the message a `float` parameter gives rather than `struct.pack`'s, and ±inf/NaN stay legal. (3) The payload's length is the structure's (8 bytes for a `c64`, 16 for a `c128`), which is what `setBytes:` copies. Pinned by `tests/test_metal_launch_path.py` (the declared `c64 value`, the parser round trip, the bytes, and the refusals) -- Metal itself cannot run off Apple hardware.

- **Metal carries the whole shared science vocabulary, and refuses the CUDA-only one by name.** `SHARED_MATH_BUILTINS` and `SHARED_MATH_TEMPLATES` are keyed by backend, so every entry now has a `metal` spelling: MSL declines the `f`-suffixed CUDA forms and spells the fast approximations `fast::` (`fast::sin`, ...) rather than OpenCL's `native_`. Two entries are deliberately not direct translations. (1) **`native_recip` is a template, not a callee**: MSL has no reciprocal intrinsic at all, so it is written as the division it is (`(1.0f / (x))`), which is why it lives in `SHARED_MATH_TEMPLATES` -- putting an expression in a table of function names would emit `1.0f / (x)(...)`. (2) **The CUDA-only families stay CUDA/HIP-only**: `fast_exp`/`exact_recip` and the conversions are not spelled for Metal, and `_emit_cuda_only_builtin` now refuses them by backend name instead of indexing the table. Both lookups that read a spelling are written as a table lookup plus an explicit `self._error` when the backend is missing -- never a bare `[self.launch_backend]`, which raised a `KeyError` from inside the translation. `tests/test_metal_launch_path.py` pins all of it: every shared entry has a metal spelling, the two tables stay disjoint, and no CUDA-only entry claims one.

## File size policy (hard rule)

**A first-party source file must stay under 500 lines, and a file that grows past 200 lines is a
signal to look at splitting it.** Every session that touches this repository holds to these two
numbers, not just the one that does the splitting.

| Band | Rule |
| --- | --- |
| <= 200 lines | The target. A file here needs no justification. |
| 201 - 350 | The watch band. Allowed, but adding to a file in this band should make you think about whether the new code belongs somewhere else. |
| 351 - 500 | The warning band. Split it before you add to it, or say why not. |
| > 500 | **The red line. Not allowed.** A first-party source file never crosses it. |

The ceiling applies to first-party `.py`, `.cl`, `.cu`, `.hip`, `.metal` and device-header
(`kernel/include/*.h`) sources. Four kinds of file are exempt, and the exemptions are stated
here so they are not argued again per file:

1. **Vendored runtime headers** - `pygpgpu/{cuda,opencl}/driver/include/*.h` (`cuda.h` is
   25,029 lines, `cl_ext.h` 3,621, `cl.h` 1,939). These are the vendor SDK headers, copied
   verbatim so the ctypes layer can be built without the SDK installed. They are never
   hand-edited.
2. **Vendored third-party source** - `pygpgpu/cparser/pcpp/**` (the bundled C preprocessor,
   ~30,000 lines including `ply/yacc.py`). Already excluded from ruff and from ty. Not ours
   to restructure.
3. **Generated Python stubs** - `**/*.pyi`. The `pygpgpu/vec_types/*.pyi` stubs are written by
   `vec_types/helper.py:write_clmath_pyi()` from the `genVecN.pyi.in` templates and are
   around 3,650 lines each because one declares 1,020 swizzle property getters and 192
   setters; a stub describes one class and cannot be assembled from parts. They are excluded
   from ruff and ty and shipped through `package-data`.
4. **Generated compile caches** - `tests/__clcache__/`, `__cucache__/`, `__hipcache__/`,
   `__metalcache__/`. Already in `.gitignore` and not tracked by git. These must not be split;
   they must be ignored.

**`line_budget.py` enforces the red line**, and it runs as the third step of `check.py` (after
ruff and ty). It walks the first-party sources, counts the lines, and fails when a file
crosses 500. It carries no allowlist: there is nothing over the line to allow. Run it after
any change that adds a file or grows one substantially.

**How to split, when a file does need it.** The rule is **by subject, never by line count**:
logic that belongs together stays in one file, logic that belongs to a different subject goes
to a different file. "It reached 500 lines, cut it here" is the wrong reason to cut, and a cut
made for that reason usually leaves two half-related modules instead of two related ones. The
mechanisms that work, in the order of preference:

1. **A package facade.** Turn `foo.py` into `foo/` whose `__init__.py` re-exports every name
   the module used to publish. Every existing import site keeps working unchanged.
2. **A mixin extraction**, for one large class. The class becomes several mixin classes in
   separate modules, combined by one class statement. `self` remains one object, so every
   `self._visit_*` call and every attribute the outside world reads keeps working.
3. **A data-module extraction**, for a class that is mostly constant tables. The tables move
   to sibling modules the class imports and assigns.
4. **A support package**, for a test file: the tests go into modules named after their
   subject, the helpers they share go to `tests/_helpers/`, and a pytest fixture goes to the
   package's `conftest.py` (a fixture has to live there to be found).

Two things to check on every split, because they are the ones that break silently: a member
defined twice in a class (a property and its setter, an overload stub and the real method)
must move **both** definitions, and a name the outside world reads by string -- a `globals()`
lookup, a `getattr` with a computed name, a test that reads a module's source text -- has to
follow the move.

`docs/file-split-plan.md` is the full plan, with the per-area layouts and the risk register.

## Layout and ownership

- `pygpgpu/kernel/`: `@kernel` decorator (`decorator.py`), Python-to-device AST translator (`translator.py`), and the device builtins (`builtins.py`). Backend-neutral except that HIP reuses CUDA generation. `python_backend.py` is the interpreter backend: it translates nothing and executes the body serially, so it is not a fourth code generator — keep it that way (no AST translation there, only the source scan that tells a magic loop from a gid-style body).
- The builtins are four files with one job each: `builtins.py` holds *only* the dual-sided functions a user may call, `builtin_registry.py` maps name <-> object for the translator, `device_builtins.py` holds how each name is emitted per backend, and `host_runtime.py` holds what the host bodies need (the per-launch frame and the flat read-modify-write). Do not add infrastructure to `builtins.py`. There is no `gpu` namespace: every builtin is exported from the `pygpgpu` top level, so an editor completes `pygpgpu.` and a type checker sees the real signature.
- A builtin call is recognized by the *object the callee resolves to* (`builtin_registry.builtin_name_of`), never by the spelling of the name, so a user's own `def dot(...)` stays an ordinary device helper while `from pygpgpu import dot`, `pygpgpu.dot(...)` and `from pygpgpu.kernel.builtins import dot` all translate as the builtin; `FunctionTranslator._builtin_call_name` is the single place that decides this. Add a builtin by defining it in `builtins.py`, listing it in `builtins.__all__`, and adding its device mapping to `device_builtins.py`; `tests/test_builtins.py` fails if the three disagree.
- **One object per builtin name, and the host and the device must agree on what it accepts.** A name pygf also publishes is *pygf's object*, re-exported by `pygpgpu/vec_types/funcs.py` — never a second implementation, because a kernel that imported one copy would translate as an ordinary device helper (whose body has no device meaning), and two host contracts for one name would make a kernel mean different things per backend. This is why `dot` is **vector-only on both sides**: pygf refuses a scalar pair, so the device refuses it too and points at `a * b`, rather than reducing it to a multiply the way it once did. **pygf is a vector library, and that bounds what the complex support may reach there**: a complex answer may live in pygf only when the name already serves vectors too (that is why `sqrt(z)`, `sign(z)`, `min(z, w)`, `conjugate(z)` are pygf's — the same functions a vector body calls), and a complex-only name would have to be hosted here instead, beside the OpenCL-only eight. When pygpgpu needs a complex answer for a name pygf *refuses* there, the host body belongs here: `pygpgpu.kernel.sci_math.rint` rounds through python's `round`, so a complex `rint(z)` is refused on both sides and the spelling is `np.rint(z)` — do not widen pygf to make that name answer one. **The rule cuts both ways, and `rint` is the worked example of it.** Once that host body answers a complex value (each part rounded with python's `round`, which is `np.rint`'s rule), the *device* may answer it too, and `COMPLEX_BUILTIN_FUNCTIONS` carries `rint` again — a builtin is refused on the device only while the host refuses it, because the interpreter runs the host body for the same call. The reverse is also load-bearing: `fmin`/`fmax` are not the ordering pair. numpy has two min/max families for NaN: `minimum`/`maximum` propagate an operand that holds a NaN (it has a defined place in the order), `fmin`/`fmax` return the other operand. A complex value is NaN when either part is, so the header carries `c64_fmin`/`c64_fmax` beside `c64_min`/`c64_max` and the emitter picks by the builtin's own name — emitting the ordering pair for `fmin` answered the wrong number whenever a NaN was involved, on a launch that looked fine.
- **Eight builtins are OpenCL-only and their host bodies live here: `select`, `isordered`, `isunordered`, `abs_diff`, `hadd`, `rhadd`, `mul24`, `mad24`.** They *are* vector operations — every one of them is component-wise — so "pygf has no such operation" is not the reason. Two other reasons are: (1) pygf is a **GLSL-shaped** function set whose spellings exist so a transpiler can map them without a rename table, and none of these eight has a GLSL spelling at all, so hosting them there would mean either adding OpenCL names to that set or inventing names for it; (2) `mul24`/`mad24` are named after a hardware instruction rather than a mathematical operation, and OpenCL leaves them undefined outside 24-bit inputs — see the scope note below. Where a host body lives is independent of whether something is a builtin: all eight keep a `device_builtins` emission and must stay dual-sided. They are still defined in `funcs.py` beside the pygf re-exports; splitting them into their own module would make the boundary visible but changes nothing semantically.
- **The host-side libraries of both backends share one binding machinery, and each brings its own tables.** `pygpgpu/libraries/` holds the backend-neutral part -- `MetaLibrary`/`Library`/`Func` (a metaclass that loads the DLL lazily, a wrapper that binds an entry point's argument and return types on first use, a returned status code turned into a `LibraryError`), `resolve_dll(dll_name, so_name, roots)` and `LibraryError`. `pygpgpu/cuda/libraries/` and `pygpgpu/hip/libraries/` each declare their own DLL names, signature tables, enums and status messages; `cuda/libraries/_base.py` is a one-line re-export of the shared module, kept so the CUDA library modules import `._base` as before. A new backend adds a package, not a copy of the machinery.
- **The HIP libraries are cuBLAS's API with hipBLAS's values, and the difference is not cosmetic.** `pygpgpu/hip/libraries/` binds hipBLAS and hipBLASLt. Four things are load-bearing. (1) **The signature tables are DERIVED from the CUDA ones** (`hipblas.hip_signatures_from`), because the argument lists really are identical and a second table would drift; every entry is **copied**, never shared, because `Func.__call__` caches the bound function in `func_info["dll_func"]` and a shared entry would hand one library another's function -- a cuBLASLt call would land in hipBLASLt. (2) **The names are not a plain prefix swap**: hipBLAS drops the ABI version suffix CUDA 12 carries (`cublasSgemm_v2` is `hipblasSgemm`), hipBLASLt spells its entry points `hipblasLt*` even though its DLL is `hipblaslt.dll`, and `GetStatusString` is absent from both -- `_symbols.hip_symbol` is the single place that decides, and a CUDA symbol with no HIP counterpart maps to `None` and is left out of the table. (3) **The VALUES are hipBLAS's own, and passing cuBLAS's is a real bug**: `HIPBLAS_OP_N` is **111** where `CUBLAS_OP_N` is 0, `HIPBLAS_STATUS_ALLOC_FAILED` is 2 where cuBLAS's is 3, and the compute types are 0..10 where cuBLAS's are 64..77. A gemm given CUDA's `OP_N` comes back `HIPBLAS_STATUS_INVALID_ENUM`. So the enums and the status messages are declared in `hip/libraries/_enums.py`, read from ROCm's headers -- never aliased to the CUDA ones. (4) **The status codes are checked by the shared machinery, not by the caller**: on Windows `ctypes.c_int is ctypes.c_long`, so `restype == c_int` is true for these entry points too and `Func.__call__` raises before a wrapper sees the status. A wrapper that wants to add a hint overrides `_context_hint_for` (which is what `HIPBLASLt` does for `INVALID_VALUE`, whose usual cause is the device rather than the arguments).
- **hipFFT, hipSPARSE and hipSOLVER are bound with their OWN signature tables, and the reason is a fact about ctypes.** Their shape is cuFFT's / cuSPARSE's / cuSOLVER's but the signatures are not, so `hip/libraries/hipfft.py`, `hipsparse.py` and `hipsolver.py` declare their entries from ROCm's headers. Five differences are load-bearing. (1) **`hipfftHandle` is a POINTER here and an `int` in cuFFT.** The header says `typedef struct hipfftHandle_t* hipfftHandle` unless `__HIP_PLATFORM_NVIDIA__` is defined, where it is `typedef int hipfftHandle`; cuFFT's `cufftHandle` is a `c_int`. A table carrying the CUDA shape passes a 4-byte integer where the library reads an 8-byte pointer -- an access violation inside the first call, which is exactly what an earlier attempt produced in `hipfftExecR2C`. (2) **Two entries differ in ARITY from the cuFFT table beside them**: `hipfftExecC2C` takes the direction as a fourth argument (the cuFFT table lists three) and `hipfftGetSize1d` takes `(plan, nx, type, batch, workSize)` (the cuFFT table lists four, without the type). (3) **hipSPARSE's `GetVersion` takes `(handle, int*)` and `CreateDnMat` takes an `order`** where the cuSPARSE tables here list one and six. (4) **hipSOLVER has no version query at all**, and the cuSOLVER table's `getrf` is itself mis-shaped (it lists a `lwork` the API does not take and omits `devIpiv`), so deriving would have carried that over. (5) **`uplo` is hipBLAS's enum, not cuBLAS's**: `HIPBLAS_FILL_MODE_LOWER` is 122 where `CUBLAS_FILL_MODE_LOWER` is 0, and a factorization given cuBLAS's value answers `INVALID_ENUM`. `hipfftType` is the exception that proves the rule -- it carries cuFFT's values (`0x2a` and friends) even though the *status codes* are numbered separately.
- **Two of those three cannot run on every device, and hipSOLVER fails SILENTLY -- do not "fix" that by adding a status check.** rocSPARSE and rocSOLVER resolve their kernels out of a runtime directory beside the DLL, and ROCm 7.2's Windows install creates one for rocBLAS (`bin/rocblas/library`, which is why hipBLAS works) and for rocFFT, and **none** for either of them. So `hipsparseCreate` answers `HIPSPARSE_STATUS_INTERNAL_ERROR` with a null handle, and `hipsolverDnCreate` **succeeds** while a factorization returns success with `devInfo == 0` and leaves the matrix untouched -- a wrong answer with no error. The library's status is the truth and there is no binding bug to look for: a caller has to check the numbers, and `hipsolverDnSgetrf_bufferSize` answering zero is the cheap tell. `tests/test_hip_libraries.py` probes the *answer* rather than the status and skips with the reason, the same way the CUDA side handles cuSOLVER's missing kernels. hipBLASLt is the third case: rocBLASLt loads its kernels from a Tensile file named after the architecture, ROCm ships those for the discrete GPUs only, and the integrated `gfx1036` of the development machine has none, so every matmul fails there while the binding is fine -- `gemm` does not depend on it.
- **The library wrappers take numpy's row-major layout and give it back.** `hip/libraries/wrappers.py` mirrors `cuda/libraries/wrappers.py`: hipBLAS reads **column-major**, and the trick is that a row-major `(R, C)` array has the same memory as the column-major matrix of shape `(C, R)` that equals its transpose. So the multiply is handed over as **A <- b's memory, B <- a's memory**, which computes `b^T @ a^T = (a @ b)^T` -- and that transpose is exactly the memory of the row-major result. The leading dimension follows from the same fact and is the array's **row length** (`lda = N`, `ldb = K`), not the inner dimension: getting that wrong is silent, because the numbers still come out as *a* product. Device memory goes through the HIP runtime the backend already uses (`hipMalloc`/`hipMemcpy`), not a second allocator, so the buffers are the ones the backend's own kernels read.
- **The scientific-computing vocabulary lives in `kernel/sci_math/`, and it is split by what the *device* has, not by what the host has.** The tables in `device_builtins.py` decide it, and **every table is keyed by backend**: `SHARED_MATH_BUILTINS` (the functions all three backends have, with each one's spelling), `SHARED_MATH_TEMPLATES` (the ones the backends spell differently, as a template per backend), `CUDA_ONLY_BUILTINS` / `CUDA_ONLY_CONVERSIONS` (the ones CUDA and HIP have and OpenCL does not), and `HIP_ROUND_TOWARD_ZERO_HELPERS` / `HIP_ROUND_TOWARD_ZERO_SOURCES` (the device helpers HIP needs because it has no intrinsic for them). Six things are load-bearing. (1) **The device's own documentation is the authority, not the spelling**: CUDA's `rhypotf` is the *reciprocal* hypotenuse (`1/sqrt(x²+y²)`), so the name here is `reciprocal_hypot`, and CUDA's `sinpif` is `sin(πx)`, not a sinc, so the name here is `sin_pi`. Both were found by running the intrinsics, not by reading the names. (2) **A name pygf publishes is pygf's object**: `ldexp`, `fract` and `sign` are re-exported from `pygpgpu/vec_types/funcs.py`, and `fma` is pygf's already published here as `mad` (OpenCL's spelling) — a second implementation would break the one-object-per-name rule. (3) **"CUDA-only" means "not OpenCL"**: HIP reuses the CUDA code generation and has these intrinsics too, so a kernel using one runs on CUDA and HIP and is refused on OpenCL *by name* (`_emit_cuda_only_builtin`), because the compiler's own "undeclared identifier" would not say which of the two the user should reach for. (4) **A vector argument is refused for the scalar-only ones** and expanded per component for the component-wise ones (`fract`, `sign`, `fmin`, `fmax`) — the device has no vector overload for `erf`/`tgamma`, but the component-wise ones work per component. (5) **HIP's generated source includes `<cmath>`**, and it has to: HIP's own device header declares only the fast intrinsics, the error function and the Bessel functions, while `fminf`/`fmaxf`/`fmaf`/`copysignf`/`remainderf`/`nextafterf`/`ldexpf`/`powf` are the C++ standard library's. Without that include a HIP kernel calling one of them fails to compile — which is exactly what `hip_compiler.py` now adds. (6) **The spelling is looked up by `launch_backend`, not by `backend`**: HIP reuses the CUDA code generation, so `backend` is "cuda" for a HIP kernel, and looking the spelling up by it would give the HIP kernel CUDA's spelling. The two differ in exactly two places — HIP has no `__exp2f` (so `native_exp2` is `exp2f` there) and HIP has none of the round-toward-zero intrinsics at all. For those three the HIP spelling is a **device helper**: it takes the correctly rounded value, uses the fused multiply-add to learn which side of it the exact result is on, and steps one unit toward zero when it is the other way. That reproduces CUDA's intrinsic bit for bit, where a plain `truncf(x / y)` would not (it truncates an already rounded quotient). The helper is a device function, so the translator emits its definition into `device_helpers` and the compile step puts it before the kernel that calls it — C needs a callee before its caller.

## Repo-specific behavior to preserve

- **A python `int`/`float` parameter has no width of its own, so `infer_ctype` chooses one — and it can be told which.** Python's `int` is arbitrary precision and its `float` is a double, but a device parameter is one fixed width, so the default is 32 bits for both. `@kernel(int=..., float=...)` and the process-wide `set_type_map()` override that, and `translator.resolve_device_type` is the single place that turns the caller's **type object** into a device type name: a numpy dtype or scalar type (`np.int64`, `np.dtype("uint32")`), a ctypes scalar class (`ctypes.c_double`), or a device type name (`"long"`). Five things are load-bearing. (1) **The allowed set is closed, it differs per key, and it reaches nothing else.** `int=` may name only the eight integer widths — `char`/`uchar`/`short`/`ushort`/`int`/`uint`/`long`/`ulong`, written `np.int8` through `np.uint64`; `float=` only `float`/`double` (`np.float32`/`np.float64`). `bool` is not an integer width, `half` is out of scope on CUDA/HIP, and a string is a *device* type name: `np.int8` is accepted while the string `"int8"` is not. Every refusal is a **`ValueError`** — a wrong type is a wrong value for this argument, not a syntax error. A numpy scalar outside a mapping names its own width and keeps it (`np.uint32(x)` stays `uint`, `np.float32` stays `float`), so the feature is an override of the two builtins rather than a competing type system; `validate_type_map` refuses any other key. (2) **A python `complex` follows `float=`, and one table decides it** (`python_complex_type` over `_COMPLEX_WIDTH_PER_REAL`): the default 32-bit real pairs with `c64` and `float=` on a double gives `c128`, so 64-bit real arithmetic is never paired with a single-precision complex value in the same body, while `np.complex64`/`np.complex128` keep their own width. Three sites choose a width for a python complex — a scalar argument/outer value (`infer_ctype`), a body literal (`3 + 4j`) and `complex(re, im)` (`FunctionTranslator._python_complex_kind`) — and all three read that one function, so a mapping moves them together; a literal or a constructor that hard-coded `c128` silently disagreed with the `float` beside it. A **device helper** is the fourth place, by way of the first two: its translator is built with the kernel's `type_map` (a helper is monomorphized *inside* the kernel's own translation unit), and `_device_func_name` folds that mapping into its hash, because one helper under two mappings is two functions — different bodies, and for a complex value even a different return type — while one generated source file carries every kernel written in that module. On the host the binding casts a python complex to the **declared record's own width** before reinterpreting it as the `c64`/`c128` record (`astype`, never `asarray(..., dtype=...)`: pygf owns the `np.asarray` name process-wide, so a wrapper that exists to add a view is not what the conversion should depend on), because viewing a 0-d complex128 as an eight-byte record is a ValueError, not a conversion. **Metal** has no such cast: it writes the record's two components itself, each through the range check a `float`/`double` parameter gets (see the Metal bullet on a complex scalar parameter). (3) **An integer that does not fit the chosen width raises `ValueError`, never wrapping.** `k(2 ** 31 + 5, out)` used to reach the device as a *negative* number with nothing reported; `_check_integer_fits` refuses it and names the numpy spelling that would carry the value (`np.int64`/`np.uint64`), and says so plainly when no device type is that wide. It is a `ValueError`, not a `SyntaxError`: the source is legal. `PyKernel._invoke` therefore trims `ValueError` to the caller's frame the way it trims `SyntaxError` — otherwise the body handler would dress an argument refusal up as a failure inside the function. (4) **The mapping is a snapshot taken when the decorator runs** (`_effective_type_map`, decorator's own over the process-wide default), never re-read at call time: `set_type_map()` must not change a kernel that already exists. (5) **It is part of the kernel's identity**, in `_source_signature` and in `_c_name` as well as the `_cache` key — it decides the declared C type, so two mappings are two translation units. Without that, the second mapping would be served the binary the first compiled. Pinned by `tests/test_kernel_type_map.py` (type-object resolution, the builtin-only rule, the complex follow, both widths' precision on a real device, and the cache separation). **The mapping reaches a structure member too, and a member's C spelling is per backend.** `objects.scalar_member_type` turns the mapping's device type name into the ctypes class a synthesized member carries (`long` is `c_int64`), so `obj.n = 2 ** 31` under `int=np.int64` no longer wraps; `objects._numeric_member_type` runs the same `translator.check_integer_range` a scalar argument does, so a value the chosen width cannot hold is refused with the member named. A **declared** `ctypes` member keeps its own class — the caller wrote that width down, and the mapping must not override it. Two traps are load-bearing. (1) **`structs.field_type` has to spell the field the way the backend spells the type**: `long` is 32-bit in CUDA C on Windows, so an `int64` member declared `long` was four bytes while the host packed eight, and reading `0x1122334455` gave `0x22334455` — the loss is silent, and `translator._CUDA_TYPE_NAMES` already carried the rewrite (`long` → `long long`) for parameters while the field emitter did not use it. `structs._backend_type_name` is the one place that decides. (2) **An imported handwritten kernel's declared scalar is width-checked before it launches** (`kernel_import._check_scalar_widths`): `_declaration_accepts` only chooses a backend, and a bracket names one outright, so `k["opencl"](256, ...)` on a `uchar` parameter reached the device and wrapped to `0`. `translator.ctypes_device_type_name` is what turns the parsed class into a device type name. Never re-introduce `np.dtype(expected).type(value)` as the check: numpy 2 raises `OverflowError` for an out-of-range value, which escaped a `(TypeError, ValueError)` handler entirely. Pinned by `tests/test_kernel_member_width.py`.
- **A python sequence is two different things, and `objects.numeric_list_as_array` is the single place that decides which.** A list/tuple **of numbers** is an *array argument*: `np.asarray` gives it numpy's own dtype (`int64`/`float64`/`complex128`) before anything looks for object members, which is what makes `k([1, 2, 3], out)` and `for x in items: total += x` work — the conversion runs at the top of `convert_object_arguments`, so the width follows the array rule and **not** the `int=`/`float=` mapping. A list of **objects** is left alone on purpose: `Scan.add_list` gives it a synthesized element structure, and that is what the ray-tracing example's `for hitable in self.hittables:` relies on (iterating it, indexing it, and calling a method on an element all work). Never convert an object list to an array — the element type would be lost. Three consequences. (1) **A numeric list as a structure member is a fixed-size array field** (`objects.numeric_list_type` returns `element * count`, numpy records it as a sub-array dtype, and `structs` writes `float values[4];`), so `bag.values[0]` and `bag.values[i]` both work; the extent is fixed by the caller's list because a C layout is decided once per dtype. (2) An empty list member, and a list-of-lists member, are refused with their own reason — neither describes an element type a field can be declared with. (3) **These structural refusals belong to the object scan, which only a device backend runs**, so a test for them takes `gpu_backend`; the interpreter backend accepts the same source and answers serially. Pinned by `tests/test_kernel_sequence_arguments.py`. **A nested list is NOT iterated level by level, and that is a deliberate gap rather than an oversight**: `for x in arr` in `_emit_element_loop` always yields one *element* (a scalar), so `for row in grid:` / `for cell in row:` has no slice type to hand the inner loop. A multi-dimensional python list must therefore be passed whole and indexed as `grid[i, j]`. Giving an element loop a slice-typed element would mean carrying an offset and a remaining-shape through it, which is a separate feature -- do not add it as a side effect of touching the sequence conversion.
- **Every work-size bracket is CUDA's, on every backend: `(blocks_per_grid, threads_per_block)`.** `k[(4, 256)]` is 4 groups of 256 threads (1024 work items), `k[(n,)]` / `k[n]` is a bare item count with an automatic group size, and `None` means automatic. This holds in `@kernel`'s bracket, in the low-level `oop` `Kernel` (`pygpgpu/{opencl,cuda,hip}/oop/kernel.py`) and in a kernel imported from `.cl`/`.cu`/`.hip` -- one spelling everywhere, because that is what a CUDA or HIP reader already writes and an OpenCL reader states a group width through `local=` in its own API rather than through a bracket. OpenCL's own enqueue call speaks a *different* pair (total item count, one group's width), so `utils.blocks_to_global` is the single place that turns `(blocks, threads)` into `(global_work_size, local_work_size)`; CUDA/HIP `oop` kernels already take `(grid_dims, block_dims)`, which is the same pair under their own names. Two consequences are load-bearing. (1) The total always divides by the group width -- the quotient *is* the block count -- so there is no divisibility check to make, and a bracket that "did not divide" is no longer representable. (2) A CUDA/HIP launch derives `grid_dims = global // local`, which is `blocks` by construction, so all three backends launch the same grid from the same bracket. `global` is never a block count and never a bare total under CUDA's spelling: it is always `blocks * threads`.
- Automatic work sizes are chosen in `utils.py` (`detect_work_size` / `local_size_for_global`): the local size comes from the extents (or their divisors) and is clamped to the device's real limits, preferring warp-aligned groups. The derived `global` is intentionally **not** required to equal the array length: when a bounds guard is guaranteed (`@kernel` always emits one) the global may be rounded up to a multiple of the local, which keeps work groups efficient for awkward extents such as prime lengths. Do not "fix" this rounding back to exact equality.
- Handwritten kernels must clamp themselves against the real element count passed as an argument. `get_global_size(dim)` reports the (rounded) launch size, not the buffer length, so it is not a valid bound; see `examples/vecadd.cl`.
- A gid-style kernel (`get_global_id`) has no loop for the automatic work size to read a domain from, so it must declare one: `@kernel(domain="x")`, part of the **signature**, where that fact belongs. (It used to have a second spelling, a `work_size(x)` statement in the body, and that has been **removed** -- the statement sat inside a *device* function body while meaning nothing to the device.) The domain contributes all of `x`'s dimensions, and a `k[(total, local)]` bracket is the other way to state the launch shape. Without any of these the launch raises instead of falling back to a buffer-shape guess (the original auto-detection picked a buffer by write flags, and that guess silently launched a 1-work-item grid for a 100000-element reduction). **A domain of more than three axes folds into one flat launch axis of `prod(shape)` work items**, which is what the original auto-detection did -- a grid has no fourth axis. What that means for the body is the difference between the two ways of iterating: a magic loop recovers the original axes by decomposing the flat position, while a gid-style body reads the flat position directly (`get_global_id(0)` is it and the higher axes read 0). So a rank-4 domain is legal either way, and a body that wants the original axes spelled out should iterate with `np.ndindex` rather than index `get_global_id` itself. `@kernel(domain=...)` validates at compile time: the name must be one of the function's parameters, it must be an array (a scalar has no shape to give), and the body may not also carry a magic loop -- one declaration per kernel.
- **The traversal rank and the launch rank are independent.** A magic loop names a position in its own domain; the launch supplies ids along its axes. They used to have to match, which made a 3-D loop in a 1-D grid write 3 of 60 elements (the loop read one index per launch axis, and a 1-D grid holds the others at 0) and made a loop of more than three axes impossible at all. `_emit_nd_head` now always emits the same two steps: fold the launch's ids into **one flat work-item position**, then decompose that position over the loop's domain (`i / s1 / s2 / s3` for the slowest axis, `i % s_last` for the fastest -- the exact inverse of the row-major flattening `_nd_flat_index` emits). Three things are load-bearing. (1) The fold is written per axis as `(id % grid_extent)` and combined with the extents between axes, so a grid that has only axis 0 populated folds to its own gid and an N-D grid of the same total gives the same position -- the generated source therefore does not depend on the launch rank at all, which it must not: a bracket is **not part of the cache signature**, so a source compiled for one launch shape would otherwise be reused for another. (2) `%` and `*` share a precedence level in C and associate left, so every group in that expression needs its own parentheses; leaving them out produced `expected a ")"` from NVRTC. (3) The flat position's name is fixed (`_work_position`), not built from the loop's `param`, because that argument may itself be an expression (`(self)->image_height` for a receiver member) rather than a C identifier. The host side follows: a loop of more than three axes has its extents multiplied into one flat launch axis, and an explicit bracket is checked for **coverage** rather than for rank -- a launch enumerating fewer work items than the loop traverses is refused (it would silently leave part of the domain unvisited), while a larger one is accepted because the per-axis bounds guard skips the excess. Axis order no longer matters either; it is just another way to spell the same total.
- **Shared (work-group) memory is `buf = zeros_per_group(shape, dtype)` (or `zeros_per_block`, the same function), indexed by the group first: `buf[blockIdx][...]`.** The arguments are `np.zeros`'s own and in its own order -- **shape first, dtype second** (`zeros_per_group(256, np.int32)`, `zeros_per_group((64, 64), np.float32)`) -- and the shape may be an int or a tuple of them, so a multidimensional buffer indexes as `buf[blockIdx][i, j]` or, equivalently, as `buf[blockIdx][i][j]`: a single subscript consumes one axis and hands back a slice carrying the remaining axes plus the offset so far, which is how the nested spelling reaches the same element. The shape must be a **compile-time constant** (a literal int or tuple; a module constant is refused too), because the buffer is a fixed-size `__shared__` array on CUDA/HIP and one `__local` parameter on OpenCL, so a launch-time size cannot declare it.  The value stands for **every group's slice at once**, so the model is honest on both sides. On the **host** it really is a mapping -- block id to that group's array -- which is why the first subscript is required; on the **device** it produces no index arithmetic at all: the emitted code is a plain `__shared__` array (CUDA/HIP) or `__local` parameter (OpenCL), which the hardware already gives each group privately, so `buf[blockIdx][j]` folds to `buf[j]`. `_visit_shared_slice` therefore **validates** the group subscript rather than computing one (it must be `blockIdx` or `get_group_id(d)`, or a local assigned from one), and any other index is refused: emitting that as an offset would read the **next** group's copy, which is exactly the memory a work item must never touch. Two consequences are load-bearing: `_is_local_buffer` accepts both the buffer and its slice (`bins[blockIdx]`), because an atomic call passes the slice and answering False there made the OpenCL cast say `__global`, which the compiler rejects as a change of address space; and a bare `buf` is refused, since naming the whole mapping has no device meaning. A shape built from a name is refused for the same reason: `zeros_per_group(GROUP, np.float32)` is refused with "zeros_per_group() shape must be a constant positive integer or a tuple of them" even when `GROUP` is a module constant (which is why `examples/09_reduction.py` mirrors its `GROUP` by hand). The dtype must be a numpy one (`np.int32`, or the string `"int32"`); `half` is refused. A `barrier()` is required between the write phase and the read phase -- without it a work item reads a slot another group member has not written yet. **The interpreter backend runs it too**, and keeps the groups apart: the value it returns is a real mapping (block id to that group's `np.zeros`), created on first use and refused for a block id the launch does not have. A `barrier()` is still a no-op there, so a body that depends on another work item having written first gets the serial answer rather than a device one.
- **CUDA's index names are `int3` values, not calls: `blockIdx`, `threadIdx`, `blockDim`, `gridDim`.** A CUDA programmer reaches for `blockIdx.x`, and a ported kernel should not have to be rewritten, so each is published as a three-axis vector whose components are the same numbers the OpenCL spellings give per axis (`blockIdx.x` is `get_group_id(0)`, `threadIdx.x` is `get_local_id(0)`, `blockDim.x` is `get_local_size(0)`, `gridDim.x` is `get_num_groups(0)`). They are **values**, so no parentheses: `buf[blockIdx][j]` and `blk = blockIdx.x`. A value cannot hold a per-launch number, so on the host these are lazy `_IndexVector` objects reading the current launch frame; the device does not see that class at all -- `_visit_name` resolves the **name** through `INDEX_VECTOR_BUILTINS` (CUDA) or `INDEX_VECTOR_OPENCL` and emits the vector directly, so the two sides cannot disagree. One detail is load-bearing: `_IndexVector.__hash__` must not evaluate the readers, because the object is a registry key (`BUILTIN_NAMES_BY_FUNCTION`) and hashing it during import would ask for a launch frame that does not exist yet.
- **The python backend's work sizes really split the domain for the id queries.** `PythonFrame` carries the launch's global and local sizes, so `get_group_id`/`get_local_id` divide by the group size exactly as a device run does -- a bracket `k[(8, 4)]` reports two groups, `k[(8, 2)]` four -- and `blockIdx`/`threadIdx` report those same numbers, because they delegate to the scalar spellings rather than assuming a single block. **Only the queries are affected**: a magic-loop body still runs once, over the array's real extent, because the loop *is* the launch there (`_serial_sizes` supplies the group size, nothing else). A magic-loop body's ids answer the launch's first work item rather than raising, so `blockIdx.x` reads `0` and `threadIdx.x` reads `0`; a gid-style body (`@kernel(domain=...)` or a bracket) walks the domain one work item at a time and every id is real. Do not make the work size change what a magic loop iterates: that is the one thing the two arrangements must keep agreeing on.
- **A builtin call with a complex argument is settled before any type table is consulted, because those tables are keyed by type and a complex value has no entry in any of them.** `_emit_gpu_builtin` (the package's vocabulary) and `_emit_builtin` (python's builtins) both hand a complex-carrying call to `_emit_complex_builtin` first. Without that gate the tables answered with the real path's spelling -- `sqrtf(z)`, `powf(z, w)`, `min((int)(z), (int)(w))`, `fminf(fmaxf(z, 0.0f), 1.0f)`, `((z) * (w)) + (v)` -- which is a C call the compiler cannot type, or (for `round`) an expression that silently returned the value unchanged. Four tables decide the answer, and **the split is numpy's, because the interpreter runs pygf's helper for the same name**: `COMPLEX_BUILTIN_FUNCTIONS` (complex in, complex out: the transcendental family, `conjugate`, `pow`, `sign`, which is the direction on the unit circle), `COMPLEX_BUILTIN_REAL_RESULTS` (`abs`, the magnitude), the pairwise/ternary rules in the emitter (`min`/`max`/`fmin`/`fmax` are the header's lexicographic compare, `clamp`/`saturate`/`mix`/`mad` are built from it), and `COMPLEX_BUILTIN_REFUSALS` (the names numpy and the interpreter both refuse, each with the spelling to use instead). **`sign` is a complex result, not a real one** -- putting it beside `abs` emitted `c64_from_real((float)(c64_sign(z)))` and the compiler refused the record-to-real cast. A real operand in a complex call is widened through the header (`min(z, 1.0)`, `np.clip(z, 0, 1)`, `pow(z, 2)`), and a mixed `c64`/`c128` pair is computed at the wider width. **`round(z)` is refused while `np.round(z)` answers**, because python's builtin `round` has no complex form in the interpreter and numpy's does: the numpy branch emits the header's `rint` directly rather than routing through the builtin table, where `rint` is this package's own name and rounds through python's `round()` (so it is refused like it). The `np.*` spellings that had their own emitters carry the same gate -- `np.minimum`/`np.maximum` (lexicographic), `np.clip` (`None` bound means the operation on that side is absent), `np.isnan`/`isinf`/`isfinite` (either part / both parts, in `_emit_complex_math`), `np.power` (a complex base or exponent). Pinned by `tests/test_kernel_complex.py`: every one of them runs against numpy on all backends, and the refusals are checked at translation time.
- **A body with several magic loops is several *passes*, translated into one kernel each and launched in order.** `magic_loop_phases` splits the body at every top-level magic loop after the first (the first is the dispatch), `_translate_phase_kernels` translates each slice on its own translator, and `render_kernels` names them `<kernel>_p0`, `<kernel>_p1`, ... in one source. This is the answer to "split into nested launches, or a CUDA graph?": neither. A nested launch is CUDA-only, and a graph has to be built on the host and re-instantiated per shape, so either would make a plain two-phase body CUDA-only; consecutive launches work on **every** backend and cost only a launch per phase. Two consequences are load-bearing: each phase kernel declares only the shapes *it* indexes, so its launch arguments are rebuilt from `kernel_shapes` rather than reusing the first kernel's list (a later pass commonly names an array the first never does); and the arrays a pass boundary does not need on the host stay on the device (see the read-back bullet below). Three things about the split itself are load-bearing. (1) **Each pass is its own generated-source piece.** `_compile_write` writes one piece per rendered kernel; joining them into one piece made the merge (which keys a definition by its signature line) replace only the first pass's group and leave the file's later passes in place, so the file held them twice and the next compile refused them ("already been defined"). (2) **A phase translator is built with what the main one was built with**: the receiver structure (`self_struct_members`/`self_struct_type`), `struct_arg_classes`, `type_map` and the whole outer-scope binding. Without the receiver, every *method* body with a second loop failed the argument-count check; without the outer binding, a slice that read a global without repeating its `global` statement declared it read-only while the launch handed it the writable slot. The loop extents of a multi-pass body also live on the phase translators, so `work_size_members` comes from `shapes_owner` (phase 0), not from the main translator, which never visits a loop. (3) **A pass's complex needs come from the phase translators too**: `_compile_write` folds in every phase's `complex_needs`, because the main translator's own set is empty -- reading only it generated `c128_mul`/`c128_add` calls with no declaration, which is what a two-pass body that iterates a complex value hit. What the earlier single-kernel form did instead was emit the second loop as an ordinary serial loop **inside** every work item: N items each ran the whole phase and raced on the same array, which is why the shapes that happened to agree still read as correct.
- **A pass boundary copies nothing home unless host code needs it, and the policy is `kernel/decorator/_phase_readback.py`.** Between two passes the device holds the newest bytes, so a read-back followed by an upload copies twice for nothing. `deferred_arrays` keeps an array on the device by binding it through a `gnp.ndarray` view over the caller's own memory -- the deferred machinery the binding layer already has (`_mark_device_written` plus `to_host`) -- and `flush_deferred` brings its bytes home once, after the last pass; the asynchronous chain flushes at the same point. Two filters decide what is deferred, and both are load-bearing. (1) **A non-contiguous array is excluded**: its device copy is a *compacted* staging buffer, so writing those bytes back through the view landed in the wrong place -- the caller's view came back unmodified and the buffer behind it scrambled. (2) **An array a host region or the tail names is excluded.** A host region is python, so an array it names has to be current before it runs; the scan is a plain "is this name mentioned", which is enough because a region that needs the bytes necessarily loads them, and an alias (`view = a`) names the array on the binding statement. The scan covers `phase_gaps` and `body_tail` -- the regions a launch actually runs between passes and after the last one. `tests/test_phase_readback.py` pins both halves for contiguous plain arrays and `gnp` arrays on every backend, and asserts the *position* of the copies rather than their count -- a round trip still ends with one home copy, so counting alone cannot tell the two apart. Two measured facts about this policy are worth keeping in mind: the Mandelbrot example's two-pass body has no host statement between its loops, so it pays one upload at the start and one read-back at the end and nothing in between; and a plain array gets this by being viewed as `gnp`, so the compatibility with `gnp` is verified, not assumed.
- **A host region that reaches an array through something other than its own name is a known gap, and it is older than the read-back policy.** The scan above asks whether a *region* mentions the array. A body can publish the array somewhere else on the host -- `SHELF.append(a)` above the first loop, then `read_shelf()` inside a gap -- and the gap's own statements then name nothing the scan can link to `a`. Measured: the device answers a stale value (the region read the caller's input where python reads the previous pass's output), and it does so **with the deferred path disabled as well**, so this is not a cost of the read-back policy. The likely reason is that the object the host statement stashed and the object the launch binds are not the same array object, so their host bytes are different buffers. Widening the scan to every host statement in the body (header included) was attempted and made `gnp` arrays answer a wrong result, which is why the scan stays where it is. The behaviour is therefore documented and not tested: a body that needs a host region to see a device-written array must name the array in that region. Do not widen the scan without re-running `tests/test_phase_readback.py`'s indirect cases against `gnp`.
- **A scalar initialized above the magic loop and updated *inside* it is one location for the whole launch, not one per work item.** This is the reduction shape every tutorial starts with and the quietest way a kernel can differ from python: a plain `int total` is per work item, so N items each accumulate one element and the answer is one work item's partial sum -- `total = 0; for i in ...: total += x[i]; out[0] = total` read `[1]` instead of `[10]`, with nothing in the program looking wrong. `_carried_scalars` finds such a name and `_bind_carried_scalars` gives it a one-element buffer (`T*`), the same shape a writable outer scalar already uses: the body reads and writes `name[0]`, and the host reads the final value back. Three details are load-bearing. The **criterion** is that the name is read *after* the loop -- a name used only inside it is per-item scratch, and sharing it would turn a deterministic value into a race (`return total` inside the loop returns what this work item accumulated). The **update must be atomic** (`total += x[i]` becomes `atomicAdd(total, ...)`), because every work item writes the one location. And the **initializer is not re-emitted**: `total = 0` already ran on the host, and `_visit_statement` skips it, or it would reset the shared slot for every work item and overwrite the parameter's type. `total = total + x[i]` (a plain assignment) is *not* converted -- the racy check lives in `_visit_augassign`, so the `+=` spelling is what reaches it.
- **A host region is python, so its statements run once, at the moment python would, and everything it changes must land where python would put it.** Four rules are load-bearing. (1) **A statement runs exactly once, in the region itself.** `_host_region_values` executes the region at assembly time too, but only to learn *which* statements the host can run; on the caller's own arrays that discovery run applied the store a second time and, worse, before the first pass -- `x[0] = x[0] + 1` then shifted the data the first launch uploaded. The discovery run works on copies (`_isolated`), and a value the region computes is refreshed from the launch-time run. (2) **An assignment to a kernel parameter reaches the later passes and leaves the caller's variable untouched**, because a parameter is python's function-local. It is not a gap slot: a slot for the parameter shadowed the update in the argument alignment. (3) **A writable outer name's slot is the only carrier for it** -- the device writes that slot and the region's write-back fills it, so a second gap slot for the same name kept the launch reading the old value. (4) **The loop extents, the tail and the region all read the same launch frame**; `_sync_device` waits before every launch for the same reason, since the caller may have written the host arrays since the last call.
- **`submit()`/`async_call()` run every pass of a multi-pass body, chained on the backend's own completion events.** `_phase_async` submits pass 0 and attaches a done-callback; each callback hands the continuation to a shared worker pool rather than running it inline, because a CUDA stream callback may not call the driver API and the next pass *is* a driver call. The worker binds the device context (a driver call from a fresh thread needs it), runs the portable host region for the boundary it just crossed, and submits the next pass; the last pass's completion runs the deferred flush, the outer write-back, the object write-back and the tail, then settles the caller's future (`concurrent.futures.Future` for `submit`, `asyncio.Future` for `async_call`). No thread ever waits on the GPU, and the chain is one launch per pass plus one worker hand-off per boundary. Before this the two forms refused a multi-pass body outright.
- **A body may return a plain scalar after the magic loop when that scalar is a carried slot.** The statements after the loop run once per work item, which is why a value computed there used to be refused -- it would be one work item's. A carried scalar removed that reason: it is one location for the whole launch, so every work item's copy of the expression is the call's result, and the claim word hands back the one value. `_return_is_shared` decides this by walking the returned expression's names: a carried slot or a kernel argument qualifies (both are launch-wide), anything else is one work item's own and stays refused. `best = x[i]` inside the loop is the shape that cannot work -- only `+=` becomes an atomic, so a plain store into the shared slot races -- and `_non_atomic_writes` refuses it with the race named, instead of compiling and answering whichever work item finished last.
- **A body's statements run in three host regions; only the loop bodies are device code.** The statements above the first loop, between two loops, and after the last loop are python, executed once each on the host: above at launch-assembly time, between passes (`_run_host_region` runs region i after launch i and syncs the device first, because the previous pass's read-back is a stream callback), and the tail after the last launch -- for a single-loop body the tail is `translator.body_tail`, recorded in `_translate_magic_loop` for every dispatch shape and run once the launch has finished. A tail `return` is evaluated on the host after the other tail statements (a bare `return` cannot be exec'd, so the runner skips Return statements in the exec loop and evaluates the expression at the end), and python's "first return wins" holds: an in-loop return claims the result on the device, and the tail's return only answers when no work item claimed one. The tail reads created arrays whole -- they travel in a separate `created_objects` map, because unwrapping a created array with `slot[0]` would hand the statements its first element or row instead of the object. Whatever a host statement reads must be current: an array a previous pass wrote is pulled back before the statement runs and pushed again for the next launch, and a gap statement may write what the next pass reads. `_sync_device` waits before every launch for the same reason -- the caller may have written the host arrays since the last call, and the upload reads their memory. `_carried_scalars` still decides which scalar travels as a shared slot, with one addition: a phase that *writes* a name the whole body carried keeps the slot even though its own slice cannot see the read (`phase_carried_hint`). A gap creation (`middle = np.zeros(4)` between loops) travels as the object itself, never as a scalar slot. Two traps are load-bearing. The phase launch aligns arguments to each phase's own signature (`phase_param_names`), but only for names declared *before* the shape extents -- outer-scope values and host-created objects are declared after them and the trailing blocks append those, so including them would shift every argument. And python truthiness must never decide whether a slot exists: `bool(np.array([0]))` is False, which made a zero-valued slot read as missing (`a or b`) and silently skipped the write-back.
- **A kernel may launch another kernel from device code: `inner[(total, local)](args)`.** This is CUDA's dynamic parallelism, and it is the one feature that needs a **device-code link**: the child kernel is resolved through the device runtime, so NVRTC's image is not enough. A source that nests a launch is therefore built by **nvcc** instead (`_compile_linked_cuda` in `decorator.py`), and everything else keeps using NVRTC -- the cost, a subprocess and a dependency on the toolkit, is paid only where the feature is used. Three details are load-bearing. (1) `-cubin` is **not** sufficient: for a nested source nvcc leaves the *parent* out of that image (only the child is listed), because the device link runs during the **host** link; so the build goes through a throwaway executable with a stub `main` and the device image is extracted with `cuobjdump -xelf`. (2) nvcc compiles `.cu` as C++, where `__global__ void f(...)` gets a **mangled** symbol while the host looks the kernel up by the plain name it generated; the linked copy therefore spells every entry point `extern "C"` (and only that copy -- an NVRTC source must keep the name it already resolves). (3) `Kernel` begins with an empty argument layout that a `Program` fills while fetching its kernels, so `_LinkedImage` hands the parsed layout over directly (`kernel.args = kernel_infos[c_name].args`), from the same `ProgramParser` the NVRTC path uses. The bracket carries at most `(total, local)` and **only** the work size: the backend and the device cannot be chosen from device code, because the device is already running. Only **cuda** supports it -- the OpenCL kernel language has no nested-launch statement at all, and HIP does not offer it on this platform -- and both refuse with a message naming dynamic parallelism. The `python` backend runs the call as an ordinary call, which is what a serial run means. A `@kernel` called *without* a work size is refused, because from device code it is a launch and not a helper.
- `@kernel` specialization is per backend + device + argument type signature, compiled at first call rather than decoration. Kernels need retrievable Python source: define them in real `.py` files, not stdin/`exec` strings (`inspect.getsource`).
- **`@kernel` keeps the decorated function's parameter list, for the editor and for a type checker.** A kernel is a callable *object*, so what an editor suggests on a call comes from the object's type rather than from the `def` that was decorated; publishing plain `PyKernel` as the decorator's result made a checker read the decorated name as the **decorator** (`(f) -> PyKernel`), so `k(a, b, out)` was checked against `__call__(*args, **kwargs)` and a call with a missing argument was accepted silently. The fix is PEP 612: `PyKernel`, `_KernelCall`, `_BoundKernelMethod` and `_native_argument_errors` are generic over `_P` (the decorated function's parameters, `_R` its result), and both decorator spellings are declared as `@overload`s so the function's own signature lands on the decorated name. Five things are load-bearing. (1) A user-defined generic over a ParamSpec needs **Python 3.10+**, and this package supports 3.7+, so `_KernelBase` is `Generic[_P]` inside `if TYPE_CHECKING` and a plain class whose `__class_getitem__` returns itself at runtime — subscripting `PyKernel[_P]` at import must never fail, and the runtime base is the one that answers, not a proxy. (2) The annotated branch has to be a **class definition**, not an alias (`_KernelBase = Generic[_P]`): `ty` reports `unbound-type-variable` for the alias form and then reads the whole class as `Unknown`, so the hints disappear even though pyright still resolves them. (3) `_native_argument_errors` forwards `_P`/`_R` explicitly — `functools.wraps` alone makes a checker report `(*args, **kwargs)`, which would undo the signature one layer down. (4) `_BoundKernelMethod` (what `PyKernel.__get__` returns for an instance) is deliberately **loose**: the decorated method's `P` still carries the receiver, no descriptor can drop it, and spelling `P` there made every correct `obj.method(x, y)` report "missing argument 'y'" because `self` was counted. The class form `Klass.method(obj, x, y)` keeps its full signature (that access is `PyKernel` itself), and `__get__` says so with two overloads keyed on `obj: None` vs `obj: object`. (5) `PyKernel.__init__` takes `Callable[..., Any]`, not `Callable[_P, Any]`: a caller can build one directly, and `P` is not bound in that position. Pinned by `tests/test_kernel_typing.py` (the runtime half) and by `python check.py` (the checker-visible half).
- Helper functions called from a kernel need no decorator and no annotations: `_emit_device_call` translates them into device functions and monomorphizes per call-site argument types, recursively. Emission order must be dependency order (`_dependency_order` in `decorator.py`) because C requires a callee before its caller and the cache fills depth-first. A helper defined in `python -c`/stdin has a `<string>` filename and yields an invalid C identifier, so keep helpers in real `.py` files.
- All three backends can be used in one process, and the same `PyKernel` object caches one specialization per backend + device + signature. Keep that working: do not add process-wide backend state (Taichi-style `init(arch=...)` global config), and keep backend package imports lazy so importing `pygpgpu` still needs no GPU runtime. The `python` backend takes part in the same bracket dispatch but caches nothing (there is nothing to specialize) and is never probed as a default, so a machine without a GPU keeps raising instead of silently falling back to the interpreter.
- The `python` backend's launch semantics must stay in step with the GPU ones: a magic-loop body runs once as written, a gid-style body runs once per work item of its `@kernel(domain=...)` domain or `(total, local)` bracket, and each builtin resolves through the thread-local frame in `host_runtime.py` so concurrent launches never share a work item. That frame holds only the launch shape and the current work item; the operations themselves are the bodies in `builtins.py`.
- Static read/write analysis (`KernelFlags` in `constants.py`, implemented in `ts_parser.py`) decides which arguments are uploaded/downloaded. Do not defeat it when adding argument handling. A written buffer is always *also* uploaded: the download copies the whole buffer back, so a buffer that was never uploaded would replace every element the kernel did not write with a fresh device buffer's zeros, losing what the caller had. An argument explicitly declared `write_only` is the only exception.
- **Integer `//` and `%` carry python's floor semantics, and the device emits a helper to get them.** C's `/` truncates toward zero and its `%` takes the dividend's sign, so the two disagree the moment an operand is negative (`-7 // 2` is `-4` in python and `-3` in C; `-7 % 2` is `1` and `-1`). `FunctionTranslator._emit_floored` is the single place that decides, and both the binary operator and the augmented form (`//=`, `%=`) route through it -- `//=` used to be a plain `/=`. The correction is the standard identity (differ by exactly one step only when the remainder is non-zero and the operands' signs differ), emitted as a device function from `PYTHON_FLOOR_SOURCES`, which keeps one division rather than two. Three details are load-bearing. (1) **The qualifier is per backend** (`PYTHON_FLOOR_QUALIFIERS`): the definition goes into every generated source that uses it, so a file holding several kernels would otherwise carry several non-`inline` copies, which C++ rejects -- and CUDA/HIP need `__device__` on top of `static inline` or the function is a host one. (2) **The name is built from `c_identifier_suffix`**, not from the C type: `long long` cannot appear verbatim in an identifier, so the helper is `__pygpgpu_floor_div_longlong`. (3) **An unsigned width emits no helper at all** -- its remainder is never negative, `(r < 0)` on it is always false (and some compilers warn), and the plain C operator already agrees. Pinned by `tests/test_kernel_floor_division.py`, which runs signed int32/int64, unsigned uint32, and both augmented forms.
- `arr[i] op= value` becomes a device atomic operation whenever the translator cannot prove the element is private to the work item (`FunctionTranslator._augassign_is_race_free`). The proof is deliberately narrow: the subscript must be built from exactly the magic loop's index variables, each once. Anything else — a data-driven index like `bins[image[i]] += 1`, a partial tuple, an arithmetic index — is racy, and a plain read-modify-write there silently loses contributions (a histogram written that way counted 256 of 4096 pixels per channel). Only operators with an atomic counterpart are accepted (`+=`, `-=`, `&=`, `|=`, `^=`); a racy `*=`/`/=`/`**=` or a racy float accumulation raises a `SyntaxError` telling the user to use an integer buffer or a reduction, because atomic float is not implemented on OpenCL here.
- **An atomic's index is a flat offset, and a tuple index is flattened to one.** `atomic_add(a, i, v)` is row-major, so on a `(2, 3)` array `i = 5` writes `a[1][2]` -- a scalar index is already flat and is left alone, which is why the 1-D spelling keeps working on a multidimensional array. `atomic_add(a, (i, j), v)` names the axes and flattens over the **declared** shape, the same way `a[i, j]` does, so the two spellings agree. Two things are load-bearing there: the tuple has to be flattened **instead of** visited as an expression (`_flatten_index` is called before `ast.Tuple` reaches `_visit_expression`, which has no device value for a tuple), and the interpreter's `_flat_position` flattens the same tuple over the real shape, or the two sides disagree. An atomic on shared memory names the group's slice (`atomic_add(buf[blockIdx], (i, j), v)`), because the slice carries the shape the flattening needs -- a bare `buf` has none. A partly indexed slice (`buf[blockIdx][i]` on a 2-D buffer) is a slice rather than an element, so using it where a scalar is required is refused by `_scalar_position` instead of emitting a buffer with no subscript.
- An outer scalar (`nonlocal`/`global`) is **always** racy, since every work item shares the one location, so `counter += 1` on it is always emitted as an atomic and the result is written back after the call. Two things this depends on: outer scalars are stored as `name[0]` rather than `(*name)` (`_visit_target`), because the read/write analysis only recognizes the subscript form as a write and otherwise leaves the buffer un-read-back — the host then kept its initial value; and `atomic_add(counter, 0, 1)` is **refused** with a message pointing at `counter += 1`, because atomic operations index an array. A 1-element array remains the spelling that works for an explicit atomic on a caller-owned scalar.
- **The copy policy is decided per argument by the read/write analysis, and it has two rules.** (1) **A written buffer is always uploaded too**, because the read-back copies the *whole* buffer into the caller's array: a buffer that was never uploaded would replace every element the kernel did not write with the contents of a fresh device buffer (zeros), and python keeps those. That is why an explicit `write_only` qualifier does **not** skip the upload -- it describes what the body may assume, not an instruction to stop copying, and `_param_flags` therefore ignores it. The return claim/site words are no exception even though the library owns them: `atomicCAS(&_ret_claim[0], 0, 1)` *reads* the word to compare against zero, so a slot that was never uploaded would decide the claim against whatever the device buffer held. (2) **A buffer the body neither reads nor writes is copied neither way**, so its flags are `KernelFlags(0)` and both `need_upload` and `need_read_back` are False. Each backend's `VarInfo` owns those two properties (`{cuda,hip,opencl}/oop/program_info.py`), `use_buffer` consults `need_upload`, and `Buffer.bind_data` records the host pointer *without* transferring when the copy is skipped -- `set_data` is what binds that pointer, and a read-back with no destination fails with an invalid device-to-host copy. The analysis has to be right for rule (2) to be safe, which is why a pointer that escapes keeps both directions. Related: the same array under two argument names of one launch (`k(b, b)`) binds one buffer once (`seen_arrays` in `_process_arg`); binding it twice hit `mem obj is still in using`.
- Importing `pygpgpu` monkey-patches `numpy.array` process-wide to support nested `ctypes.Structure` values. Keep that behavior unless the change is deliberate.
- **`pygpgpu.numpy` (gnp) is the device-resident array layer, and its state machine lives in `numpy/ndarray.py`.** A *family* is one numpy buffer plus every view of it; it owns `data` (the root's bytes as one contiguous array -- the caller's memory when the root owns it, a refreshed copy when the root is a strided view), `epoch` (bumped on every content change, host or device), `current_epoch` (the epoch the host bytes reflect, so `current_epoch < epoch` means exactly "a device holds newer content"), and a reader/writer gate held while a copy or launch reads the host bytes. Each view object holds at most one `_Binding` per `(backend, device, layout)` -- the buffer plus the epoch it holds -- and "current" is one integer comparison against the family's epoch, so one bump invalidates every other device copy at once. Six things are load-bearing. (1) **The backend never reads or writes the old `dirty_on_device` flags**: it calls `_mark_device_written(mem_obj)` in `__after_call`, naming the buffer the launch actually used, because an array resident on two devices has a binding for each and only the one the kernel ran on holds the new content. (2) **A gnp binding is not pool-owned**, so `use`/`unuse` are not run for a gnp argument (they police one claim per launch, and the array reuses its own buffer across launches); running them raised "mem obj is not in using" from the driver's completion callback. (3) **A cross-device copy always stages through the host** -- backends' buffers are unrelated types and two devices of one backend can live in different contexts -- and the newest binding is the one to download from, which is what makes a host read after writes on two devices answer the second one's result. (4) **Every wait is explicit and local**: `to_device`/`to_host` start a copy on the backend's *asynchronous* pool and return a `Transfer`; the engine waits before reading host bytes another copy is writing, before launching on a queued upload, and on any host-side read (`__getitem__`, the numpy protocols, `tolist`, ...), which is why an un-awaited `to_host()` is still correct. (5) **OpenCL completion needs the already-finished check**: appending to `on_completed_callbacks` without testing `event.finished` first loses a copy that completed before the callback was registered, and `clEnqueueReadBuffer` must stay **non-blocking** (`blocking_read=False`), because a blocking read enqueued from inside a driver event callback deadlocks. (6) **`np.asarray`/`np.ascontiguousarray` return a plain ndarray sharing the array's memory without going through any protocol method** -- a numpy subclass fact that cannot be intercepted -- so the engine routes its own host access through `_ensure_host_bytes()`, and `array_creation`'s wrappers do the same for every constructor and argument. Those wrappers must keep returning **gnp** arrays: `np.zeros(...)` is numpy's own function and yields a plain array with no device residency, which is why the two namespaces stay separate.
- **A gnp argument keeps its own object all the way through a launch; the backend must not convert it to a contiguous ndarray.** Every backend's `__prepare_call` ran `np.ascontiguousarray(value)` on a non-contiguous argument, and `np.ascontiguousarray(gnp_array)` returns a **plain** ndarray: the launch then uploaded a temporary copy, orphaned the array's own device buffer, and the kernel's writes never reached the caller (a `base[:, 0]` column read back unchanged). The guard is `isinstance(value, gnp.ndarray)`, and the same holds for the dtype cast. **A non-contiguous gnp view is handled by `_member_bytes()`**: when the view's bytes do not form a window inside the family it keeps a private contiguous copy (`offset == -1`), and `_absorb` scatters the downloaded values back **through the view's own layout** (`np.copyto(view, ...)`) -- writing them contiguously into the family buffer shifts every row and loses the assignment.
- **Zero-copy is offered only where the driver guarantees the device addresses the caller's own bytes, and refused with the reason elsewhere.** `zero_copy_support(backend)` answers from the *backend* (not from this machine's devices, which may be absent), and `to_device(zero_copy=True)` raises `NotImplementedError` naming the backend. CUDA/HIP use `cuMemHostRegister_v2`/`hipHostRegister` with the devicemap flag plus `...GetDevicePointer`, and Metal's `StorageModeShared` buffer *is* host memory (the allocation checks that the two addresses agree). **OpenCL is refused**: `CL_MEM_USE_HOST_PTR` lets the runtime keep a private copy, so a kernel write might never reach the array. Four details. (1) A registration covers a whole **page**, so `_register_range` tracks `(backend, page_start)` and its extent: two arrays on one page share the pin, and a page already pinned over fewer bytes is **widened** (unregister then register over the range this caller needs) rather than refused -- the driver reports `CUDA_ERROR_HOST_MEMORY_ALREADY_REGISTERED` as its only reliable "already pinned" signal, including for a registration this table never made, so that refusal is what triggers the takeover. (2) A registered buffer's handle is a *device address of host memory*, never allocated, so its release is re-pointed at `cuMemHostUnregister`/`hipHostUnregister` -- the buffer class's own finalizer would free a pointer it does not own. (3) The registration is made on the **current** context, so `make_current()` runs before the driver call. (4) `torch.Tensor` interop lives in `numpy/_torch.py` under the same rule: a CPU tensor and a host-resident array can share one buffer, while a CUDA tensor's storage is torch's and the request raises.

- Caches live beside the source (`__clcache__`, `__cucache__`, `__hipcache__`; generated `@kernel` sources under `.../pykernels`). Each generated file has a **`.source-digest` sidecar** recording the digest of the python text it came from, and a mismatch restarts the file; the mtime is only the cheap first test, because `git checkout` and `git stash pop` restore a file *and* set its mtime back, which used to keep a file written from newer text looking fresh (its stale kernel declaration then sat beside the new one). The digest is a sidecar, **never a comment in the source**: that text is a translation unit whose blank lines `_split_source` splits on, so inserting a line into it changes how a later write re-reads the file -- doing exactly that broke every structure declaration whose typedef block came after the marker. A kernel's C name hashes the module, the argument types **and the rendered parameter list** (`translator.parameter_declarations()`), folded into one hash so the name stays `name_<hash>`: the generated signature carries extents, outer-scope values and shared buffers that the argument types do not, and hashing only the types left a body whose derived signature had changed under its old name -- two declarations of it in one file, which C++ rejects. All caches can still be deleted when debugging stale generated code.
- Handwritten-kernel `.pyi` stubs are regenerated next to the source on import; `examples/vecadd.pyi` comes from `examples/vecadd.cl`, `examples/kernel_import/vecops.pyi` from the three `vecops.*` sources. Edit the kernel/parser, never the generated stub.
- **The caches are shared by threads *and* processes, so every step that touches one is serialized.** `tests/test_kernel_concurrent_compile.py` is the regression net. One python module owns one generated file, and each kernel it defines is appended to that file on its own first call, so concurrent cold compiles are the normal case, not a corner. Five things are load-bearing. (1) **`source_paths.write_lock` wraps the read-merge-write**: `append_source`/`write_source` read the file, merge the definitions this call rendered, and write it back, and an unserialized writer based its merge on a file that no longer held what the other one added -- the later write then erased a sibling's definition and its launch reported `KeyError` naming the kernel it could not find. It holds a per-file `threading.RLock` **and** an OS-level `.lock` file beside the target (`os.open` with `O_CREAT|O_EXCL`), because threads share memory and processes do not. The lock is re-entrant **per thread** (`_file_lock_state`): an exclusive create has no notion of "already mine", so a nested acquisition would wait on a lock this thread is holding -- a 600-second deadlock, which is exactly what a helper compiled inside its caller's critical section produced. (2) **The compile is inside that same lock** (`PyKernel._compile`): the cached binary is keyed on the file's *content*, so a compile starting between two appends cached a binary of a half-populated file. (3) **Every cache write is atomic** (`utils._atomic_write`: temp file then `os.replace`, temp name carrying pid and thread id) -- a reader that saw a truncated artifact failed with `CL_INVALID_KERNEL`; `os.replace` refusing with a Windows sharing violation is retried briefly and then falls back to a plain overwrite. (4) **`save_var`'s meta readers tolerate a missing or unreadable file** (a re-parse, not a failure): `_load` of the three `program_parser` modules catches `OSError`/`EOFError`/`UnpicklingError`/`ValueError`/`TypeError`. (5) **`os.makedirs(..., exist_ok=True)` is not atomic on Windows** -- it can still raise `FileExistsError` for a segment another writer just created -- so `utils._ensure_directory` raises the levels one at a time and re-checks the filesystem after each failure. Two driver-side lazies were part of the same bug and are now locked: the device and platform enumeration (`MetaDevices` in cuda/hip, `MetaPlatforms` and `Platform.__fetch_devices` in opencl -- two concurrent enumerations returned `CL_DEVICE_NOT_FOUND` on a machine that plainly had a device, rather than merely repeating the work), and `Program._fetch_kernels`, which now creates each kernel **by name** (`clCreateKernel`) instead of enumerating whatever the program holds, since a cached binary can predate a sibling kernel and `clCreateKernelsInProgram` then answers `CL_INVALID_VALUE`. **`Kernel._call` holds `_arg_lock` across bind-and-enqueue on every OpenCL kernel**: `clSetKernelArg` writes the arguments onto the shared kernel handle, so two threads binding at once overwrote each other's and the launch read the other thread's buffers -- the caller's array stayed at its initial value, an all-zero result on a launch that "succeeded" (CUDA/HIP pass `value_ptrs` per call and have no such state). The bracket state was already thread-local (`_call_state`); the handle never was.
- Regenerate the vector-type stubs with `python -m pygpgpu.vec_types.helper`; templates are `genVecN.pyi.in`.
- **A generated definition whose body changed is replaced, not skipped; a definition's pieces travel together.** `append_source`/`merge_source` keep the definitions a file already holds -- a module has many kernels, and each is written by its own call -- but "already holds" has to mean **the same text**. A definition's C name hashes its *signature*, so a package-side change to what is generated from the same python source keeps the name and changes the body: a python value's width following a different mapping, a builtin emitting a different call, a fix to the emitter. Skipping there left the file describing code this package no longer generates, and the file is what the compiler reads -- the python-source digest cannot catch it, because the caller's `.py` did not move. `_merge_definitions` therefore groups the file's blank-line pieces behind the definition they belong to (a generated magic loop emits its bounds guard, a blank line, then the rest of the body, so a definition's tail is a piece with no identity of its own -- and `_definition_identity` answers only for a *declaration* line, because that tail piece may itself start with `if (atomic_cmpxchg(...) == 0)` or `while (((b < n)))`, which is a `(` with no `;`, exactly a header line's shape) and replaces a changed definition **in place**, so the callee-before-caller order the file is built in survives; an unchanged render stays byte-identical, which is what keeps the no-op write skipped. Pinned by `tests/test_kernel_generated_source_cache.py`.
- **`KERNEL_TRANSLATING` is a compile-time switch, the translator's `typing.TYPE_CHECKING`.** It is `False` in python and `True` while a body is translated, so `if KERNEL_TRANSLATING:` is the **device** branch and `if not KERNEL_TRANSLATING:` is **python's**. `builtins._translation_truth` resolves the condition and `_translation_branch` keeps exactly one side, emitted **inline** -- no `if` and no braces reach the generated source, and the dropped branch is never translated, so python-only code under the switch (a `len(str(...))`, a host lookup) costs the device nothing. The interpreter backend needs no special case: it runs the body as written, and the constant is already False there. **The trigger is the name, never the object it resolves to**: a body that declares its own `KERNEL_TRANSLATING = 0` gets the same treatment, because that is what writing the name asks for and requiring an import would only lengthen the spelling -- which is also why the decision is made on source text, so the translator imports nothing to make it. A condition that merely *mentions* the name alongside something undecidable (`KERNEL_TRANSLATING and x > 0`) stays an ordinary device `if`: the device would have to evaluate the rest, and silently picking a branch there would be a guess. `tests/test_kernel_translation_switch.py` pins both sides, the dropped-branch compilation, and the user-defined-name case.

## What only a Mac can verify

- **The whole Windows-side surface is checked; what remains needs the framework.** On a machine without Metal the backend is tested through source generation, the declaration scanner, the type tables, the cache, the import hook and the error paths. Four things cannot be reached without `Metal.framework` and a real GPU, and each has a test that will start exercising it as soon as one is present. (1) **`newLibraryWithSource:options:error:`** -- the MSL the translator emits has been checked by compiling it as C++14 (`tests/metal_syntax_check.py`), which catches structural errors but not the attribute/address-space semantics Metal enforces; a real build is what proves the prelude's macros expand onto the declared parameters. (2) **Pipeline construction** -- `newFunctionWithName:` and `newComputePipelineStateWithFunction:error:` are wired and their ownership is balanced, but whether a generated signature is one a pipeline accepts is a device question. (3) **`dispatchThreadgroups:threadsPerThreadgroup:`** -- the bracket-to-`MTLSize` mapping is unit-tested for every spelling (`k[n]`, `k[(n,)]`, `k[(4, 256)]`, the per-axis tuples, the automatic default); that the dispatch then executes those work items is not. (4) **`setBytes:`/`setBuffer:`** -- the two binding paths and the scalar widths are pinned, and a real launch is what proves a scalar parameter really reads its value rather than a pointer. `tests/test_metal_launch_path.py` and `tests/test_metal_codegen.py` skip the device-dependent assertions off macOS and run them on it, so a Mac run reports what was previously unverified rather than starting from scratch. Two features stay unimplemented until that run: **images** (the host-side `MTLTexture` binding is the missing piece -- the generator refuses the parameter so nothing silently mis-compiles) and **asynchronous launch** (the future-based forms need a completion handler on the command buffer).

## Known scope limits

- `@kernel` does not support strings/lists/dicts, recursion, or dynamic multi-dimensional indexing; unsupported syntax raises a plain `SyntaxError` positioned at the offending line. These limits belong to the GPU translator: the `python` backend runs the body as-is and accepts such code, with two exceptions: `get_global_id` inside a magic-loop body (there is no current work item there) and a kernel that creates an array inside the body, which the device lifts to a host parameter and the interpreter rebuilds per work item.
- Kernel return values travel as *parameters*, not as a C return value: a launch is N work items, so the translator gives every returned position a slot (a one-element buffer for a value, the array object itself for an array) plus one shared claim word, and the first work item to reach a `return` claims the result with an atomic compare-and-swap. The winning site records its own shape, so different `return` statements may return different arities and types; a bare `return` yields None, and the `python` backend mirrors "first non-None result wins". Read the slots back on the host, and deliver an async result in the future's completion callback — never before launch completion. A value-returning `return` after the magic loop is refused *unless* the value is a launch-wide slot -- a carried scalar or a kernel argument -- because then every work item computes the same answer (see `_return_is_shared`).
- Outer-scope variables are parameterized, never inlined (`FunctionTranslator._bind_outer_variables`): a free variable or module global the body reads becomes a plain device parameter, refreshed every call so a changed value is visible; one declared `nonlocal`/`global` becomes `T*` with every use dereferenced and the final value written back to its cell / the module globals after the call. A helper called from a kernel gets the same parameters and the call site forwards them. Rebinding an outer array is refused; writing its elements is fine and reads back through the normal `KernelFlags` analysis.
- **A kernel body is three regions, and each runs a different number of times.** The magic loop (`for i in range(arr.shape[0])`, `enumerate(arr)`, `np.ndindex`/`np.ndenumerate`) is what divides them: statements **above** it and **below** the last one run once on the host (see the three-host-regions rule), and the loop body is emitted **once per work item**. A value `return` after the last loop is therefore allowed exactly when `_return_is_shared` says the value is launch-wide; an array return stays allowed because every work item names the same object. The magic loop itself does not survive as a loop: `for i in range(arr.shape[0])` becomes one work item per `i`, with the index expressed through `blockIdx`/`blockDim`/`threadIdx`, plus the bounds guard `if (i >= extent) return;`.
- **`break` and `continue` mean what their enclosing loop is, and the magic loop is not one.** `FunctionTranslator._visit_loop_exit` is the only place that decides, from `self.loop_depth` -- the count of real C loops (`_push_scope_block(..., is_loop=True)` for `while` and nested `range`, and the element loop's own block), which the magic dispatch deliberately does not increment. Three cases: inside a real loop the statement is emitted verbatim (`continue;`/`break;`); directly in a work item `continue` becomes a plain `return;` (the same control flow -- this work item stops, the next one is another thread), and `break` raises a `SyntaxError`, because stopping the magic loop means stopping every other work item too and they are already running in parallel. **The `continue` must not be routed through `_visit_kernel_return`**: that one emits the atomic claim, so a work item merely skipping its turn would race the value-returning sites and could answer `None`. It is emitted as a bare `return;`, which is what the bounds guard already uses. The python backend needs no change: it runs the body as written, where `continue` already skips the iteration and `break` already stops the loop -- the GPU side is what had to catch up, and `break` stays a translation error because the device genuinely cannot express it.
- **The return claim/site words are declared only when a `return` reaches device code.** `_has_device_return` decides it (a `return` in a magic loop's body counts, one in the tail or in a gap between loops does not), and `render_return_params` omits the two words when it is false. This is not cosmetic: a body whose only `return` sits after the magic loop hands its value back through the host tail (`_run_host_region`), so no work item ever reaches the claim, the word stays zero, and the pair would be two uploads plus two never-read parameters. Three consequences are load-bearing. (1) `_claims_on_device` is per **phase**, because every phase of a multi-loop body is its own kernel and a pass whose only return is in its tail does not claim -- `phase_claims`/`main_claims` carry that to the launch, which appends the words only for a phase that declares them. (2) A multi-loop body's tail lives on the **last phase** (`phase.body_tail`, exposed as `phase_tail`), because `body_tail` belongs to the single-loop translation path; a body split into passes used to lose its tail entirely, so `return out` after the last loop answered `None`. (3) The words stay fully bidirectional whenever they *are* declared (`atomicCAS(&_ret_claim[0], 0, 1)` reads the word), which is what `tests/test_kernel_copy_policy.py` pins in both directions.
- Statements above the magic loop whose right-hand side only builds data (`np.zeros`, `np.full`, `np.arange`, `*_like`, `np.float32(...)`) are executed by the interpreter, not translated: the object is built on the host, travels as a parameter, and is handed back as the very same object when the body returns it. **A plain assignment above the loop that a creation reads is lifted and run by the host too**, so `n = 5; arr = np.zeros(n)` works: the host evaluates the assignments feeding the creation, in body order, before the launch. Only the *creation* travels to the device as a parameter -- the lifted plain assignments stay in the host namespace alone, because the work items compute them themselves and shipping them would add arguments nothing reads. Everything lifted this way is **still emitted as device code as well**; the host evaluation is an extra, not a replacement. The dependency set is closed to a fixed point (`a = 2; b = a * 2; c = np.zeros(b)` lifts all three), and only right-hand sides the host can genuinely run are lifted -- a literal, a name, attribute access, arithmetic, a subscript, a tuple. A **call** is not, because it may name a device helper whose body the host cannot run; `n = int(x.shape[0])` feeding a creation is therefore refused with `'arr' cannot be created here: ... could not be evaluated on the host; build it from values that exist at call time`, and `n = x.shape[0]` is the spelling that works. The creation's other sources are the kernel's arguments, the receiver, a module global or closure cell, and an *earlier* creation. Below the magic loop a creation runs once per work item, so it cannot be a host object: when its shape is a compile-time constant it is emitted as a **private C array** (`FunctionTranslator._emit_private_array`, initialised to match `zeros`/`ones`/`full`/`empty`, indexed like any array through a constant `_shape_var`), and a runtime extent is refused with a message rather than silently shared between work items. Keep the recognition list (`_HOST_CREATION_FUNCTIONS`) and the host-side evaluation (`_host_created_values` in `decorator.py`, which shares `_is_creation_shape`/`_is_host_evaluable` with the translator) in sync -- a constructor the translator accepts but the host cannot evaluate becomes a hard error.
- `bool` is not portable as a kernel parameter (OpenCL refuses a `_Bool` kernel argument, and the CUDA/HIP binding tables have no entry). It travels as a `uchar` with the host converting the argument, and a bool return slot is rebuilt as a python bool. `char` slots also use an unsigned byte, because OpenCL binds `char` to `ctypes.c_char` (|S1), which is not an integer array at all.
- `print()` inside a kernel is translated into device `printf` (`FunctionTranslator._emit_print`) on OpenCL and CUDA. A whole line must be **one** printf call site: every device call site owns an output buffer and the buffers are drained per call site, so a line split over several printf calls comes back interleaved with other work items. That is why a bool argument branches the line (one printf per `True`/`False`) and a real argument expands it per digit budget into a `switch` of literal formats — OpenCL rejects a computed format string, so `%.*f`/`%.*e` cannot be emitted. Keep the leaf count bounded by `PRINT_MAX_LINES`.
- `print()` is **deliberately rejected on HIP**. Do not try to "make it work" by experimenting with HIP printf kernels: on the tested ROCm 7.2 Windows machine, launching kernels that carry those printf call sites makes the AMD driver drop the device and Windows performs a display-driver reset (the machine has to be recovered). The OpenCL and CUDA paths are verified; treat the HIP rejection as the final behaviour. **`print()` is rejected on Metal for a different and equally final reason**: the generated call sites write into a *per-call-site output buffer* that the OpenCL runtime drains after the launch, and MSL has no such buffer -- Metal's `printf` goes to a log the command buffer owns and no host code here reads. Emitting them would compile and silently swallow the output, so `_emit_print` refuses with `self._metal_syntax` checked separately from HIP's `launch_backend` (Metal is not HIP's reuse case; it has its own code generation).
- HIP reuses CUDA code generation, so `FunctionTranslator.backend` is `"cuda"` for a hip kernel. Anything that depends on the **runtime** rather than the generated syntax must read `FunctionTranslator.launch_backend` (passed from `PyKernel._compile` as the real backend), which is how the HIP print rejection above is implemented. Do not test `self.backend == "hip"` — it is never true.
- Floats print in python's shortest round-trip form, and the digit count is chosen on the device (`_print_real_selector`) because it is a per-value property. `PRINT_REAL_DIGITS`, `PRINT_REAL_SCI_HI`/`_LO` and `PRINT_REAL_PLAIN_MAX` encode numpy `str()` (float32) and python `repr()` (double) notation; do not collapse this back to one fixed `%g` precision.
- fp16 arguments are unsupported on CUDA/HIP; use float32.
- `math.trunc(v)` cannot work on the **interpreter** backend: it runs the body unchanged, so the call reaches `math.trunc` with the numpy scalar that `x[i]` is, and numpy's `float32` has no `__trunc__` (`__floor__`/`__ceil__` exist, which is why `floor`/`ceil` are fine). The GPU backends translate it normally, and `np.trunc(x[i])` and pygf's `trunc` work on all four. Fixing it would mean handing array elements to the interpreter as python floats, which would change far more than this.
- `mul24`/`mad24` are only defined for 24-bit inputs, and the backends genuinely differ outside that range — OpenCL emits the truncating hardware instruction while CUDA/HIP have none and fall back to a plain multiply (`device_builtins.py` says so). Measured: `mul24(1 << 24, 2)` is `33554432` on CUDA/HIP and on the host, and `0` on OpenCL. That is conforming, since OpenCL leaves the result undefined there, but a kernel that passes a wider value gets a different answer per backend with no diagnostic. Within 24 bits all four backends and the host agree.

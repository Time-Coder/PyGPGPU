# AGENTS.md

PyGPGPU runs Python functions as GPU kernels on OpenCL (default), CUDA, and HIP, and can also run them serially in the interpreter through the `python` backend. Pure Python + ctypes, Python >= 3.7, packaged with setuptools. `README.md` is the English version (shown first on GitHub); `README.zh-CN.md` holds the Chinese version and the two link to each other at the top — when editing user-facing docs, keep both in sync.

## Language policy: English only (hard rule)

- **All comments, docstrings, error messages, log/UI text, and every other string in code must be written in English. Never generate Chinese (CJK) characters** in `.py` / `.cl` / `.cu` / `.hip` sources, generated stubs and templates (`*.pyi`, `*.pyi.in`), `examples/`, or any documentation file.
- The **only** permitted Chinese files are `README.zh-CN.md` mirrors of an English `README.md`, in any directory (currently two: repo root and `examples/`). When user-facing docs change, keep the matching mirror in sync. Nothing else may be added in Chinese, and no code, script, or tool may emit Chinese text.
- One narrow exception, and do not extend it: the native-form author name in `pyproject.toml`'s `authors` table, kept alongside the ASCII `Binghui Wang` entry used everywhere else. Machine-readable packaging metadata is the only place CJK is allowed; the ASCII form is canonical for all prose, code, and display.
- If you find Chinese in a file you are touching, translate it to English as part of that edit rather than copying the style.
- Spot check before finishing a task: search the tree for CJK codepoints (`rg -n '[\p{Han}]' --glob '!README.zh-CN.md'`) — the only acceptable hits are the two `README.zh-CN.md` mirrors and the native-form author name in `pyproject.toml`. Language bars link with the word `[Chinese]`, never CJK, so no other file needs an exemption.
- This rule is self-referential: AGENTS.md itself contains no CJK, and neither should any file you add.

## Setup and verification

- `pip install -e ".[dev]"` (dev dependencies: pytest, ruff, ty). No CI and no pre-commit hook; the feature tests live in `tests/` and run with `python -m pytest tests/ -q`. The whole-repo check is `python check.py` (runs `ruff check --fix` then `ty check` against the config in `pyproject.toml`).
- Fast checks without a GPU: `python -m compileall -q pygpgpu` and `python -c "from pygpgpu.kernel import kernel"`.
- The end-to-end smoke tests are the numbered scripts in `examples/` (each is standalone: `python examples/01_basic_kernel.py`; no backend specified means probe `cuda -> hip -> opencl`). `examples/06_handwritten_kernels.py` covers importing ONE handwritten `.cl` through `kernel_import` (single-backend case, struct parameters); `examples/15_kernel_import.py` covers the same-named three-backend case (brackets, overloads, KeyError); `examples/09_reduction.py` covers atomics, local memory and tree reductions.
- `tests/conftest.py` parameterizes every test over the `python` backend plus whichever device backends this machine has, and provides the `runner(kernel, *args)` fixture that brackets the current backend. Write a test once and it covers every backend; use the `gpu_backend` fixture for tests that need a real device.
- **A backend's runtime is initialized on a BACKGROUND thread, and its load failure is deferred to first use -- never swallowed.** Each driver module (`cuda/driver/cuda.py`, `cuda/driver/nvrtc.py`, `hip/driver/hip.py`, `opencl/driver/cl.py`) owns the same contract: `_start_init()` launches `init()` on a named thread and returns at once, `_wait_ready()` blocks on an event, and every driver call goes through `Func.__call__`, which calls `_wait_ready()` first. **Both are private and a user never calls them**: the backend package starts the thread when it is imported, and a call waits by itself. `init()` catches its own failure and records it (`MetaCUDA.last_init_error` / `MetaNVRTC` / `MetaHIP` / `MetaCL`) instead of raising: `import pygpgpu.cuda` succeeds without `nvcuda.dll`, and `kernel_import` relies on that to parse `.cu` sources on machines with no CUDA. Three things are load-bearing. (1) **The preheat inside `init()` must go through the raw DLL, not through `Func.__call__`**: init runs ON the background thread, and `Func` waits for init, so going through `Func` there would wait for itself -- a deadlock. (2) `init()` must not be called synchronously again anywhere: the thread is the only initializer (`_start_init()` is idempotent under a lock). (3) The background thread is what makes the import cheap: `cuInit` alone is ~600ms and releases the GIL, so it overlaps with the importing thread's own work; `import pygpgpu.cuda` returns in ~40ms and the wait happens at the first call. Nothing special may be added in callers to handle the recorded error -- a broken runtime fails exactly where it is used, with the driver's own OSError/RuntimeError. Do not turn `init()` back into a raising call, do not call it synchronously, and do not make `_start_init`/`_wait_ready` public.
- HIP compiles by spawning ROCm's `clang.exe` (hipRTC is unusable on the tested ROCm 7.2 Windows). Set `PYGPGPU_HIP_INCLUDES` (`os.pathsep`-separated) when MSVC/Windows SDK headers are not auto-discovered.

## Layout and ownership

- `pygpgpu/kernel/`: `@kernel` decorator (`decorator.py`), Python-to-device AST translator (`translator.py`), and the device builtins (`builtins.py`). Backend-neutral except that HIP reuses CUDA generation. `python_backend.py` is the interpreter backend: it translates nothing and executes the body serially, so it is not a fourth code generator — keep it that way (no AST translation there, only the source scan that tells a magic loop from a gid-style body).
- The builtins are four files with one job each: `builtins.py` holds *only* the dual-sided functions a user may call, `builtin_registry.py` maps name <-> object for the translator, `device_builtins.py` holds how each name is emitted per backend, and `host_runtime.py` holds what the host bodies need (the per-launch frame and the flat read-modify-write). Do not add infrastructure to `builtins.py`. There is no `gpu` namespace: every builtin is exported from the `pygpgpu` top level, so an editor completes `pygpgpu.` and a type checker sees the real signature.
- A builtin call is recognized by the *object the callee resolves to* (`builtin_registry.builtin_name_of`), never by the spelling of the name, so a user's own `def dot(...)` stays an ordinary device helper while `from pygpgpu import dot`, `pygpgpu.dot(...)` and `from pygpgpu.kernel.builtins import dot` all translate as the builtin; `FunctionTranslator._builtin_call_name` is the single place that decides this. Add a builtin by defining it in `builtins.py`, listing it in `builtins.__all__`, and adding its device mapping to `device_builtins.py`; `tests/test_builtins.py` fails if the three disagree.
- **One object per builtin name, and the host and the device must agree on what it accepts.** A name pygf also publishes is *pygf's object*, re-exported by `pygpgpu/vec_types/funcs.py` — never a second implementation, because a kernel that imported one copy would translate as an ordinary device helper (whose body has no device meaning), and two host contracts for one name would make a kernel mean different things per backend. This is why `dot` is **vector-only on both sides**: pygf refuses a scalar pair, so the device refuses it too and points at `a * b`, rather than reducing it to a multiply the way it once did.
- **Eight builtins are OpenCL-only and their host bodies live here: `select`, `isordered`, `isunordered`, `abs_diff`, `hadd`, `rhadd`, `mul24`, `mad24`.** They *are* vector operations — every one of them is component-wise — so "pygf has no such operation" is not the reason. Two other reasons are: (1) pygf is a **GLSL-shaped** function set whose spellings exist so a transpiler can map them without a rename table, and none of these eight has a GLSL spelling at all, so hosting them there would mean either adding OpenCL names to that set or inventing names for it; (2) `mul24`/`mad24` are named after a hardware instruction rather than a mathematical operation, and OpenCL leaves them undefined outside 24-bit inputs — see the scope note below. Where a host body lives is independent of whether something is a builtin: all eight keep a `device_builtins` emission and must stay dual-sided. They are still defined in `funcs.py` beside the pygf re-exports; splitting them into their own module would make the boundary visible but changes nothing semantically.
- **The host-side libraries of both backends share one binding machinery, and each brings its own tables.** `pygpgpu/libraries/` holds the backend-neutral part -- `MetaLibrary`/`Library`/`Func` (a metaclass that loads the DLL lazily, a wrapper that binds an entry point's argument and return types on first use, a returned status code turned into a `LibraryError`), `resolve_dll(dll_name, so_name, roots)` and `LibraryError`. `pygpgpu/cuda/libraries/` and `pygpgpu/hip/libraries/` each declare their own DLL names, signature tables, enums and status messages; `cuda/libraries/_base.py` is a one-line re-export of the shared module, kept so the CUDA library modules import `._base` as before. A new backend adds a package, not a copy of the machinery.
- **The HIP libraries are cuBLAS's API with hipBLAS's values, and the difference is not cosmetic.** `pygpgpu/hip/libraries/` binds hipBLAS and hipBLASLt. Four things are load-bearing. (1) **The signature tables are DERIVED from the CUDA ones** (`hipblas.hip_signatures_from`), because the argument lists really are identical and a second table would drift; every entry is **copied**, never shared, because `Func.__call__` caches the bound function in `func_info["dll_func"]` and a shared entry would hand one library another's function -- a cuBLASLt call would land in hipBLASLt. (2) **The names are not a plain prefix swap**: hipBLAS drops the ABI version suffix CUDA 12 carries (`cublasSgemm_v2` is `hipblasSgemm`), hipBLASLt spells its entry points `hipblasLt*` even though its DLL is `hipblaslt.dll`, and `GetStatusString` is absent from both -- `_symbols.hip_symbol` is the single place that decides, and a CUDA symbol with no HIP counterpart maps to `None` and is left out of the table. (3) **The VALUES are hipBLAS's own, and passing cuBLAS's is a real bug**: `HIPBLAS_OP_N` is **111** where `CUBLAS_OP_N` is 0, `HIPBLAS_STATUS_ALLOC_FAILED` is 2 where cuBLAS's is 3, and the compute types are 0..10 where cuBLAS's are 64..77. A gemm given CUDA's `OP_N` comes back `HIPBLAS_STATUS_INVALID_ENUM`. So the enums and the status messages are declared in `hip/libraries/_enums.py`, read from ROCm's headers -- never aliased to the CUDA ones. (4) **The status codes are checked by the shared machinery, not by the caller**: on Windows `ctypes.c_int is ctypes.c_long`, so `restype == c_int` is true for these entry points too and `Func.__call__` raises before a wrapper sees the status. A wrapper that wants to add a hint overrides `_context_hint_for` (which is what `HIPBLASLt` does for `INVALID_VALUE`, whose usual cause is the device rather than the arguments).
- **What the HIP binding deliberately does NOT cover, and why.** hipFFT, hipSPARSE and hipSOLVER are **not bound**: their entry points load, but their signatures are not cuFFT's / cuSPARSE's / cuSOLVER's in every case (hipFFT's plan handle and its exec call in particular), so a table copied from the CUDA side binds symbols it cannot then call -- which is exactly what the first attempt produced (an access violation inside `hipfftExecR2C`). They need their own tables. And **hipBLASLt cannot compute on every device**: rocBLASLt loads its kernels from a Tensile file named after the architecture (`TensileLibrary_lazy_<arch>.dat`) and ROCm ships those for the discrete GPUs only, so on the integrated `gfx1036` of the development machine every matmul fails inside rocBLASLt while the binding is fine (`gemm` does not depend on it). The test skips with that reason rather than failing, and the error message says so because the status code is `INVALID_VALUE` and would otherwise point at the arguments.
- **The library wrappers take numpy's row-major layout and give it back.** `hip/libraries/wrappers.py` mirrors `cuda/libraries/wrappers.py`: hipBLAS reads **column-major**, and the trick is that a row-major `(R, C)` array has the same memory as the column-major matrix of shape `(C, R)` that equals its transpose. So the multiply is handed over as **A <- b's memory, B <- a's memory**, which computes `b^T @ a^T = (a @ b)^T` -- and that transpose is exactly the memory of the row-major result. The leading dimension follows from the same fact and is the array's **row length** (`lda = N`, `ldb = K`), not the inner dimension: getting that wrong is silent, because the numbers still come out as *a* product. Device memory goes through the HIP runtime the backend already uses (`hipMalloc`/`hipMemcpy`), not a second allocator, so the buffers are the ones the backend's own kernels read.
- **The scientific-computing vocabulary lives in `kernel/sci_math.py`, and it is split by what the *device* has, not by what the host has.** The tables in `device_builtins.py` decide it, and **every table is keyed by backend**: `SHARED_MATH_BUILTINS` (the functions all three backends have, with each one's spelling), `SHARED_MATH_TEMPLATES` (the ones the backends spell differently, as a template per backend), `CUDA_ONLY_BUILTINS` / `CUDA_ONLY_CONVERSIONS` (the ones CUDA and HIP have and OpenCL does not), and `HIP_ROUND_TOWARD_ZERO_HELPERS` / `HIP_ROUND_TOWARD_ZERO_SOURCES` (the device helpers HIP needs because it has no intrinsic for them). Six things are load-bearing. (1) **The device's own documentation is the authority, not the spelling**: CUDA's `rhypotf` is the *reciprocal* hypotenuse (`1/sqrt(x²+y²)`), so the name here is `reciprocal_hypot`, and CUDA's `sinpif` is `sin(πx)`, not a sinc, so the name here is `sin_pi`. Both were found by running the intrinsics, not by reading the names. (2) **A name pygf publishes is pygf's object**: `ldexp`, `fract` and `sign` are re-exported from `pygpgpu/vec_types/funcs.py`, and `fma` is pygf's already published here as `mad` (OpenCL's spelling) — a second implementation would break the one-object-per-name rule. (3) **"CUDA-only" means "not OpenCL"**: HIP reuses the CUDA code generation and has these intrinsics too, so a kernel using one runs on CUDA and HIP and is refused on OpenCL *by name* (`_emit_cuda_only_builtin`), because the compiler's own "undeclared identifier" would not say which of the two the user should reach for. (4) **A vector argument is refused for the scalar-only ones** and expanded per component for the component-wise ones (`fract`, `sign`, `fmin`, `fmax`) — the device has no vector overload for `erf`/`tgamma`, but the component-wise ones work per component. (5) **HIP's generated source includes `<cmath>`**, and it has to: HIP's own device header declares only the fast intrinsics, the error function and the Bessel functions, while `fminf`/`fmaxf`/`fmaf`/`copysignf`/`remainderf`/`nextafterf`/`ldexpf`/`powf` are the C++ standard library's. Without that include a HIP kernel calling one of them fails to compile — which is exactly what `hip_compiler.py` now adds. (6) **The spelling is looked up by `launch_backend`, not by `backend`**: HIP reuses the CUDA code generation, so `backend` is "cuda" for a HIP kernel, and looking the spelling up by it would give the HIP kernel CUDA's spelling. The two differ in exactly two places — HIP has no `__exp2f` (so `native_exp2` is `exp2f` there) and HIP has none of the round-toward-zero intrinsics at all. For those three the HIP spelling is a **device helper**: it takes the correctly rounded value, uses the fused multiply-add to learn which side of it the exact result is on, and steps one unit toward zero when it is the other way. That reproduces CUDA's intrinsic bit for bit, where a plain `truncf(x / y)` would not (it truncates an already rounded quotient). The helper is a device function, so the translator emits its definition into `device_helpers` and the compile step puts it before the kernel that calls it — C needs a callee before its caller.

## Repo-specific behavior to preserve

- **Every work-size bracket is CUDA's, on every backend: `(blocks_per_grid, threads_per_block)`.** `k[(4, 256)]` is 4 groups of 256 threads (1024 work items), `k[(n,)]` / `k[n]` is a bare item count with an automatic group size, and `None` means automatic. This holds in `@kernel`'s bracket, in the low-level `oop` `Kernel` (`pygpgpu/{opencl,cuda,hip}/oop/kernel.py`) and in a kernel imported from `.cl`/`.cu`/`.hip` -- one spelling everywhere, because that is what a CUDA or HIP reader already writes and an OpenCL reader states a group width through `local=` in its own API rather than through a bracket. OpenCL's own enqueue call speaks a *different* pair (total item count, one group's width), so `utils.blocks_to_global` is the single place that turns `(blocks, threads)` into `(global_work_size, local_work_size)`; CUDA/HIP `oop` kernels already take `(grid_dims, block_dims)`, which is the same pair under their own names. Two consequences are load-bearing. (1) The total always divides by the group width -- the quotient *is* the block count -- so there is no divisibility check to make, and a bracket that "did not divide" is no longer representable. (2) A CUDA/HIP launch derives `grid_dims = global // local`, which is `blocks` by construction, so all three backends launch the same grid from the same bracket. `global` is never a block count and never a bare total under CUDA's spelling: it is always `blocks * threads`.
- Automatic work sizes are chosen in `utils.py` (`detect_work_size` / `local_size_for_global`): the local size comes from the extents (or their divisors) and is clamped to the device's real limits, preferring warp-aligned groups. The derived `global` is intentionally **not** required to equal the array length: when a bounds guard is guaranteed (`@kernel` always emits one) the global may be rounded up to a multiple of the local, which keeps work groups efficient for awkward extents such as prime lengths. Do not "fix" this rounding back to exact equality.
- Handwritten kernels must clamp themselves against the real element count passed as an argument. `get_global_size(dim)` reports the (rounded) launch size, not the buffer length, so it is not a valid bound; see `examples/vecadd.cl`.
- A gid-style kernel (`get_global_id`) has no loop for the automatic work size to read a domain from, so it must declare one: `@kernel(domain="x")`, part of the **signature**, where that fact belongs. (It used to have a second spelling, a `work_size(x)` statement in the body, and that has been **removed** -- the statement sat inside a *device* function body while meaning nothing to the device.) The domain contributes all of `x`'s dimensions, and a `k[(total, local)]` bracket is the other way to state the launch shape. Without any of these the launch raises instead of falling back to a buffer-shape guess (the original auto-detection picked a buffer by write flags, and that guess silently launched a 1-work-item grid for a 100000-element reduction). **A domain of more than three axes folds into one flat launch axis of `prod(shape)` work items**, which is what the original auto-detection did -- a grid has no fourth axis. What that means for the body is the difference between the two ways of iterating: a magic loop recovers the original axes by decomposing the flat position, while a gid-style body reads the flat position directly (`get_global_id(0)` is it and the higher axes read 0). So a rank-4 domain is legal either way, and a body that wants the original axes spelled out should iterate with `np.ndindex` rather than index `get_global_id` itself. `@kernel(domain=...)` validates at compile time: the name must be one of the function's parameters, it must be an array (a scalar has no shape to give), and the body may not also carry a magic loop -- one declaration per kernel.
- **The traversal rank and the launch rank are independent.** A magic loop names a position in its own domain; the launch supplies ids along its axes. They used to have to match, which made a 3-D loop in a 1-D grid write 3 of 60 elements (the loop read one index per launch axis, and a 1-D grid holds the others at 0) and made a loop of more than three axes impossible at all. `_emit_nd_head` now always emits the same two steps: fold the launch's ids into **one flat work-item position**, then decompose that position over the loop's domain (`i / s1 / s2 / s3` for the slowest axis, `i % s_last` for the fastest -- the exact inverse of the row-major flattening `_nd_flat_index` emits). Three things are load-bearing. (1) The fold is written per axis as `(id % grid_extent)` and combined with the extents between axes, so a grid that has only axis 0 populated folds to its own gid and an N-D grid of the same total gives the same position -- the generated source therefore does not depend on the launch rank at all, which it must not: a bracket is **not part of the cache signature**, so a source compiled for one launch shape would otherwise be reused for another. (2) `%` and `*` share a precedence level in C and associate left, so every group in that expression needs its own parentheses; leaving them out produced `expected a ")"` from NVRTC. (3) The flat position's name is fixed (`_work_position`), not built from the loop's `param`, because that argument may itself be an expression (`(self)->image_height` for a receiver member) rather than a C identifier. The host side follows: a loop of more than three axes has its extents multiplied into one flat launch axis, and an explicit bracket is checked for **coverage** rather than for rank -- a launch enumerating fewer work items than the loop traverses is refused (it would silently leave part of the domain unvisited), while a larger one is accepted because the per-axis bounds guard skips the excess. Axis order no longer matters either; it is just another way to spell the same total.
- **Shared (work-group) memory is `buf = zeros_per_group(shape, dtype)` (or `zeros_per_block`, the same function), indexed by the group first: `buf[blockIdx][...]`.** The arguments are `np.zeros`'s own and in its own order -- **shape first, dtype second** (`zeros_per_group(256, np.int32)`, `zeros_per_group((64, 64), np.float32)`) -- and the shape may be an int or a tuple of them, so a multidimensional buffer indexes as `buf[blockIdx][i, j]` or, equivalently, as `buf[blockIdx][i][j]`: a single subscript consumes one axis and hands back a slice carrying the remaining axes plus the offset so far, which is how the nested spelling reaches the same element. The shape must be a **compile-time constant** (a literal int or tuple; a module constant is refused too), because the buffer is a fixed-size `__shared__` array on CUDA/HIP and one `__local` parameter on OpenCL, so a launch-time size cannot declare it.  The value stands for **every group's slice at once**, so the model is honest on both sides. On the **host** it really is a mapping -- block id to that group's array -- which is why the first subscript is required; on the **device** it produces no index arithmetic at all: the emitted code is a plain `__shared__` array (CUDA/HIP) or `__local` parameter (OpenCL), which the hardware already gives each group privately, so `buf[blockIdx][j]` folds to `buf[j]`. `_visit_shared_slice` therefore **validates** the group subscript rather than computing one (it must be `blockIdx` or `get_group_id(d)`, or a local assigned from one), and any other index is refused: emitting that as an offset would read the **next** group's copy, which is exactly the memory a work item must never touch. Two consequences are load-bearing: `_is_local_buffer` accepts both the buffer and its slice (`bins[blockIdx]`), because an atomic call passes the slice and answering False there made the OpenCL cast say `__global`, which the compiler rejects as a change of address space; and a bare `buf` is refused, since naming the whole mapping has no device meaning. A shape built from a name is refused for the same reason: `zeros_per_group(GROUP, np.float32)` is refused with "zeros_per_group() shape must be a constant positive integer or a tuple of them" even when `GROUP` is a module constant (which is why `examples/09_reduction.py` mirrors its `GROUP` by hand). The dtype must be a numpy one (`np.int32`, or the string `"int32"`); `half` is refused. A `barrier()` is required between the write phase and the read phase -- without it a work item reads a slot another group member has not written yet. **The interpreter backend runs it too**, and keeps the groups apart: the value it returns is a real mapping (block id to that group's `np.zeros`), created on first use and refused for a block id the launch does not have. A `barrier()` is still a no-op there, so a body that depends on another work item having written first gets the serial answer rather than a device one.
- **CUDA's index names are `int3` values, not calls: `blockIdx`, `threadIdx`, `blockDim`, `gridDim`.** A CUDA programmer reaches for `blockIdx.x`, and a ported kernel should not have to be rewritten, so each is published as a three-axis vector whose components are the same numbers the OpenCL spellings give per axis (`blockIdx.x` is `get_group_id(0)`, `threadIdx.x` is `get_local_id(0)`, `blockDim.x` is `get_local_size(0)`, `gridDim.x` is `get_num_groups(0)`). They are **values**, so no parentheses: `buf[blockIdx][j]` and `blk = blockIdx.x`. A value cannot hold a per-launch number, so on the host these are lazy `_IndexVector` objects reading the current launch frame; the device does not see that class at all -- `_visit_name` resolves the **name** through `INDEX_VECTOR_BUILTINS` (CUDA) or `INDEX_VECTOR_OPENCL` and emits the vector directly, so the two sides cannot disagree. One detail is load-bearing: `_IndexVector.__hash__` must not evaluate the readers, because the object is a registry key (`BUILTIN_NAMES_BY_FUNCTION`) and hashing it during import would ask for a launch frame that does not exist yet.
- **The python backend's work sizes really split the domain for the id queries.** `PythonFrame` carries the launch's global and local sizes, so `get_group_id`/`get_local_id` divide by the group size exactly as a device run does -- a bracket `k[(8, 4)]` reports two groups, `k[(8, 2)]` four -- and `blockIdx`/`threadIdx` report those same numbers, because they delegate to the scalar spellings rather than assuming a single block. **Only the queries are affected**: a magic-loop body still runs once, over the array's real extent, because the loop *is* the launch there (`_serial_sizes` supplies the group size, nothing else). A magic-loop body's ids answer the launch's first work item rather than raising, so `blockIdx.x` reads `0` and `threadIdx.x` reads `0`; a gid-style body (`@kernel(domain=...)` or a bracket) walks the domain one work item at a time and every id is real. Do not make the work size change what a magic loop iterates: that is the one thing the two arrangements must keep agreeing on.
- **A body with several magic loops is several *passes*, translated into one kernel each and launched in order.** `magic_loop_phases` splits the body at every top-level magic loop after the first (the first is the dispatch), `_translate_phase_kernels` translates each slice on its own translator, and `render_kernels` names them `<kernel>_p0`, `<kernel>_p1`, ... in one source. This is the answer to "split into nested launches, or a CUDA graph?": neither. A nested launch is CUDA-only, and a graph has to be built on the host and re-instantiated per shape, so either would make a plain two-phase body CUDA-only; consecutive launches work on **every** backend and cost only a launch per phase. Two consequences are load-bearing: each phase kernel declares only the shapes *it* indexes, so its launch arguments are rebuilt from `kernel_shapes` rather than reusing the first kernel's list (a later pass commonly names an array the first never does); and the launches share one stream, so the arrays between them stay on the device -- with a `gnp.ndarray` the pending writes are marked `dirty_on_device` and the host never sees a copy until it actually reads the result. What the earlier single-kernel form did instead was emit the second loop as an ordinary serial loop **inside** every work item: N items each ran the whole phase and raced on the same array, which is why the shapes that happened to agree still read as correct.
- **A scalar initialized above the magic loop and updated *inside* it is one location for the whole launch, not one per work item.** This is the reduction shape every tutorial starts with and the quietest way a kernel can differ from python: a plain `int total` is per work item, so N items each accumulate one element and the answer is one work item's partial sum -- `total = 0; for i in ...: total += x[i]; out[0] = total` read `[1]` instead of `[10]`, with nothing in the program looking wrong. `_carried_scalars` finds such a name and `_bind_carried_scalars` gives it a one-element buffer (`T*`), the same shape a writable outer scalar already uses: the body reads and writes `name[0]`, and the host reads the final value back. Three details are load-bearing. The **criterion** is that the name is read *after* the loop -- a name used only inside it is per-item scratch, and sharing it would turn a deterministic value into a race (`return total` inside the loop returns what this work item accumulated). The **update must be atomic** (`total += x[i]` becomes `atomicAdd(total, ...)`), because every work item writes the one location. And the **initializer is not re-emitted**: `total = 0` already ran on the host, and `_visit_statement` skips it, or it would reset the shared slot for every work item and overwrite the parameter's type. `total = total + x[i]` (a plain assignment) is *not* converted -- the racy check lives in `_visit_augassign`, so the `+=` spelling is what reaches it.
- **A body may return a plain scalar after the magic loop when that scalar is a carried slot.** The statements after the loop run once per work item, which is why a value computed there used to be refused -- it would be one work item's. A carried scalar removed that reason: it is one location for the whole launch, so every work item's copy of the expression is the call's result, and the claim word hands back the one value. `_return_is_shared` decides this by walking the returned expression's names: a carried slot or a kernel argument qualifies (both are launch-wide), anything else is one work item's own and stays refused. `best = x[i]` inside the loop is the shape that cannot work -- only `+=` becomes an atomic, so a plain store into the shared slot races -- and `_non_atomic_writes` refuses it with the race named, instead of compiling and answering whichever work item finished last.
- **A body's statements run in three host regions; only the loop bodies are device code.** The statements above the first loop, between two loops, and after the last loop are python, executed once each on the host: above at launch-assembly time, between passes (`_run_host_region` runs region i after launch i and syncs the device first, because the previous pass's read-back is a stream callback), and the tail after the last launch -- for a single-loop body the tail is `translator.body_tail`, recorded in `_translate_magic_loop` for every dispatch shape and run once the launch has finished. A tail `return` is evaluated on the host after the other tail statements (a bare `return` cannot be exec'd, so the runner skips Return statements in the exec loop and evaluates the expression at the end), and python's "first return wins" holds: an in-loop return claims the result on the device, and the tail's return only answers when no work item claimed one. The tail reads created arrays whole -- they travel in a separate `created_objects` map, because unwrapping a created array with `slot[0]` would hand the statements its first element or row instead of the object. Whatever a host statement reads must be current: an array a previous pass wrote is pulled back before the statement runs and pushed again for the next launch, and a gap statement may write what the next pass reads. `_sync_device` waits before every launch for the same reason -- the caller may have written the host arrays since the last call, and the upload reads their memory. `_carried_scalars` still decides which scalar travels as a shared slot, with one addition: a phase that *writes* a name the whole body carried keeps the slot even though its own slice cannot see the read (`phase_carried_hint`). A gap creation (`middle = np.zeros(4)` between loops) travels as the object itself, never as a scalar slot. Two traps are load-bearing. The phase launch aligns arguments to each phase's own signature (`phase_param_names`), but only for names declared *before* the shape extents -- outer-scope values and host-created objects are declared after them and the trailing blocks append those, so including them would shift every argument. And python truthiness must never decide whether a slot exists: `bool(np.array([0]))` is False, which made a zero-valued slot read as missing (`a or b`) and silently skipped the write-back.
- **A kernel may launch another kernel from device code: `inner[(total, local)](args)`.** This is CUDA's dynamic parallelism, and it is the one feature that needs a **device-code link**: the child kernel is resolved through the device runtime, so NVRTC's image is not enough. A source that nests a launch is therefore built by **nvcc** instead (`_compile_linked_cuda` in `decorator.py`), and everything else keeps using NVRTC -- the cost, a subprocess and a dependency on the toolkit, is paid only where the feature is used. Three details are load-bearing. (1) `-cubin` is **not** sufficient: for a nested source nvcc leaves the *parent* out of that image (only the child is listed), because the device link runs during the **host** link; so the build goes through a throwaway executable with a stub `main` and the device image is extracted with `cuobjdump -xelf`. (2) nvcc compiles `.cu` as C++, where `__global__ void f(...)` gets a **mangled** symbol while the host looks the kernel up by the plain name it generated; the linked copy therefore spells every entry point `extern "C"` (and only that copy -- an NVRTC source must keep the name it already resolves). (3) `Kernel` begins with an empty argument layout that a `Program` fills while fetching its kernels, so `_LinkedImage` hands the parsed layout over directly (`kernel.args = kernel_infos[c_name].args`), from the same `ProgramParser` the NVRTC path uses. The bracket carries at most `(total, local)` and **only** the work size: the backend and the device cannot be chosen from device code, because the device is already running. Only **cuda** supports it -- the OpenCL kernel language has no nested-launch statement at all, and HIP does not offer it on this platform -- and both refuse with a message naming dynamic parallelism. The `python` backend runs the call as an ordinary call, which is what a serial run means. A `@kernel` called *without* a work size is refused, because from device code it is a launch and not a helper.
- `@kernel` specialization is per backend + device + argument type signature, compiled at first call rather than decoration. Kernels need retrievable Python source: define them in real `.py` files, not stdin/`exec` strings (`inspect.getsource`).
- **`@kernel` keeps the decorated function's parameter list, for the editor and for a type checker.** A kernel is a callable *object*, so what an editor suggests on a call comes from the object's type rather than from the `def` that was decorated; publishing plain `PyKernel` as the decorator's result made a checker read the decorated name as the **decorator** (`(f) -> PyKernel`), so `k(a, b, out)` was checked against `__call__(*args, **kwargs)` and a call with a missing argument was accepted silently. The fix is PEP 612: `PyKernel`, `_KernelCall`, `_BoundKernelMethod` and `_native_argument_errors` are generic over `_P` (the decorated function's parameters, `_R` its result), and both decorator spellings are declared as `@overload`s so the function's own signature lands on the decorated name. Five things are load-bearing. (1) A user-defined generic over a ParamSpec needs **Python 3.10+**, and this package supports 3.7+, so `_KernelBase` is `Generic[_P]` inside `if TYPE_CHECKING` and a plain class whose `__class_getitem__` returns itself at runtime — subscripting `PyKernel[_P]` at import must never fail, and the runtime base is the one that answers, not a proxy. (2) The annotated branch has to be a **class definition**, not an alias (`_KernelBase = Generic[_P]`): `ty` reports `unbound-type-variable` for the alias form and then reads the whole class as `Unknown`, so the hints disappear even though pyright still resolves them. (3) `_native_argument_errors` forwards `_P`/`_R` explicitly — `functools.wraps` alone makes a checker report `(*args, **kwargs)`, which would undo the signature one layer down. (4) `_BoundKernelMethod` (what `PyKernel.__get__` returns for an instance) is deliberately **loose**: the decorated method's `P` still carries the receiver, no descriptor can drop it, and spelling `P` there made every correct `obj.method(x, y)` report "missing argument 'y'" because `self` was counted. The class form `Klass.method(obj, x, y)` keeps its full signature (that access is `PyKernel` itself), and `__get__` says so with two overloads keyed on `obj: None` vs `obj: object`. (5) `PyKernel.__init__` takes `Callable[..., Any]`, not `Callable[_P, Any]`: a caller can build one directly, and `P` is not bound in that position. Pinned by `tests/test_kernel_typing.py` (the runtime half) and by `python check.py` (the checker-visible half).
- Helper functions called from a kernel need no decorator and no annotations: `_emit_device_call` translates them into device functions and monomorphizes per call-site argument types, recursively. Emission order must be dependency order (`_dependency_order` in `decorator.py`) because C requires a callee before its caller and the cache fills depth-first. A helper defined in `python -c`/stdin has a `<string>` filename and yields an invalid C identifier, so keep helpers in real `.py` files.
- All three backends can be used in one process, and the same `PyKernel` object caches one specialization per backend + device + signature. Keep that working: do not add process-wide backend state (Taichi-style `init(arch=...)` global config), and keep backend package imports lazy so importing `pygpgpu` still needs no GPU runtime. The `python` backend takes part in the same bracket dispatch but caches nothing (there is nothing to specialize) and is never probed as a default, so a machine without a GPU keeps raising instead of silently falling back to the interpreter.
- The `python` backend's launch semantics must stay in step with the GPU ones: a magic-loop body runs once as written, a gid-style body runs once per work item of its `@kernel(domain=...)` domain or `(total, local)` bracket, and each builtin resolves through the thread-local frame in `host_runtime.py` so concurrent launches never share a work item. That frame holds only the launch shape and the current work item; the operations themselves are the bodies in `builtins.py`.
- Static read/write analysis (`KernelFlags` in `constants.py`, implemented in `ts_parser.py`) decides which arguments are uploaded/downloaded. Do not defeat it when adding argument handling. A written buffer is always *also* uploaded: the download copies the whole buffer back, so a buffer that was never uploaded would replace every element the kernel did not write with a fresh device buffer's zeros, losing what the caller had. An argument explicitly declared `write_only` is the only exception.
- `arr[i] op= value` becomes a device atomic operation whenever the translator cannot prove the element is private to the work item (`FunctionTranslator._augassign_is_race_free`). The proof is deliberately narrow: the subscript must be built from exactly the magic loop's index variables, each once. Anything else — a data-driven index like `bins[image[i]] += 1`, a partial tuple, an arithmetic index — is racy, and a plain read-modify-write there silently loses contributions (a histogram written that way counted 256 of 4096 pixels per channel). Only operators with an atomic counterpart are accepted (`+=`, `-=`, `&=`, `|=`, `^=`); a racy `*=`/`/=`/`**=` or a racy float accumulation raises a `SyntaxError` telling the user to use an integer buffer or a reduction, because atomic float is not implemented on OpenCL here.
- **An atomic's index is a flat offset, and a tuple index is flattened to one.** `atomic_add(a, i, v)` is row-major, so on a `(2, 3)` array `i = 5` writes `a[1][2]` -- a scalar index is already flat and is left alone, which is why the 1-D spelling keeps working on a multidimensional array. `atomic_add(a, (i, j), v)` names the axes and flattens over the **declared** shape, the same way `a[i, j]` does, so the two spellings agree. Two things are load-bearing there: the tuple has to be flattened **instead of** visited as an expression (`_flatten_index` is called before `ast.Tuple` reaches `_visit_expression`, which has no device value for a tuple), and the interpreter's `_flat_position` flattens the same tuple over the real shape, or the two sides disagree. An atomic on shared memory names the group's slice (`atomic_add(buf[blockIdx], (i, j), v)`), because the slice carries the shape the flattening needs -- a bare `buf` has none. A partly indexed slice (`buf[blockIdx][i]` on a 2-D buffer) is a slice rather than an element, so using it where a scalar is required is refused by `_scalar_position` instead of emitting a buffer with no subscript.
- An outer scalar (`nonlocal`/`global`) is **always** racy, since every work item shares the one location, so `counter += 1` on it is always emitted as an atomic and the result is written back after the call. Two things this depends on: outer scalars are stored as `name[0]` rather than `(*name)` (`_visit_target`), because the read/write analysis only recognizes the subscript form as a write and otherwise leaves the buffer un-read-back — the host then kept its initial value; and `atomic_add(counter, 0, 1)` is **refused** with a message pointing at `counter += 1`, because atomic operations index an array. A 1-element array remains the spelling that works for an explicit atomic on a caller-owned scalar.
- **The copy policy is decided per argument by the read/write analysis, and it has two rules.** (1) **A written buffer is always uploaded too**, because the read-back copies the *whole* buffer into the caller's array: a buffer that was never uploaded would replace every element the kernel did not write with the contents of a fresh device buffer (zeros), and python keeps those. That is why an explicit `write_only` qualifier does **not** skip the upload -- it describes what the body may assume, not an instruction to stop copying, and `_param_flags` therefore ignores it. The return claim/site words are no exception even though the library owns them: `atomicCAS(&_ret_claim[0], 0, 1)` *reads* the word to compare against zero, so a slot that was never uploaded would decide the claim against whatever the device buffer held. (2) **A buffer the body neither reads nor writes is copied neither way**, so its flags are `KernelFlags(0)` and both `need_upload` and `need_read_back` are False. Each backend's `VarInfo` owns those two properties (`{cuda,hip,opencl}/oop/program_info.py`), `use_buffer` consults `need_upload`, and `Buffer.bind_data` records the host pointer *without* transferring when the copy is skipped -- `set_data` is what binds that pointer, and a read-back with no destination fails with an invalid device-to-host copy. The analysis has to be right for rule (2) to be safe, which is why a pointer that escapes keeps both directions. Related: the same array under two argument names of one launch (`k(b, b)`) binds one buffer once (`seen_arrays` in `_process_arg`); binding it twice hit `mem obj is still in using`.
- Importing `pygpgpu` monkey-patches `numpy.array` process-wide to support nested `ctypes.Structure` values. Keep that behavior unless the change is deliberate.
- Caches live beside the source (`__clcache__`, `__cucache__`, `__hipcache__`; generated `@kernel` sources under `.../pykernels`). Each generated file has a **`.source-digest` sidecar** recording the digest of the python text it came from, and a mismatch restarts the file; the mtime is only the cheap first test, because `git checkout` and `git stash pop` restore a file *and* set its mtime back, which used to keep a file written from newer text looking fresh (its stale kernel declaration then sat beside the new one). The digest is a sidecar, **never a comment in the source**: that text is a translation unit whose blank lines `_split_source` splits on, so inserting a line into it changes how a later write re-reads the file -- doing exactly that broke every structure declaration whose typedef block came after the marker. A kernel's C name hashes the module, the argument types **and the rendered parameter list** (`translator.parameter_declarations()`), folded into one hash so the name stays `name_<hash>`: the generated signature carries extents, outer-scope values and shared buffers that the argument types do not, and hashing only the types left a body whose derived signature had changed under its old name -- two declarations of it in one file, which C++ rejects. All caches can still be deleted when debugging stale generated code.
- Handwritten-kernel `.pyi` stubs are regenerated next to the source on import; `examples/vecadd.pyi` comes from `examples/vecadd.cl`, `examples/kernel_import/vecops.pyi` from the three `vecops.*` sources. Edit the kernel/parser, never the generated stub.
- Regenerate the vector-type stubs with `python -m pygpgpu.vec_types.helper`; templates are `genVecN.pyi.in`.
- **`KERNEL_TRANSLATING` is a compile-time switch, the translator's `typing.TYPE_CHECKING`.** It is `False` in python and `True` while a body is translated, so `if KERNEL_TRANSLATING:` is the **device** branch and `if not KERNEL_TRANSLATING:` is **python's**. `builtins._translation_truth` resolves the condition and `_translation_branch` keeps exactly one side, emitted **inline** -- no `if` and no braces reach the generated source, and the dropped branch is never translated, so python-only code under the switch (a `len(str(...))`, a host lookup) costs the device nothing. The interpreter backend needs no special case: it runs the body as written, and the constant is already False there. **The trigger is the name, never the object it resolves to**: a body that declares its own `KERNEL_TRANSLATING = 0` gets the same treatment, because that is what writing the name asks for and requiring an import would only lengthen the spelling -- which is also why the decision is made on source text, so the translator imports nothing to make it. A condition that merely *mentions* the name alongside something undecidable (`KERNEL_TRANSLATING and x > 0`) stays an ordinary device `if`: the device would have to evaluate the rest, and silently picking a branch there would be a guess. `tests/test_kernel_translation_switch.py` pins both sides, the dropped-branch compilation, and the user-defined-name case.

## Known scope limits

- `@kernel` does not support strings/lists/dicts, recursion, or dynamic multi-dimensional indexing; unsupported syntax raises a plain `SyntaxError` positioned at the offending line. These limits belong to the GPU translator: the `python` backend runs the body as-is and accepts such code, with two exceptions: `get_global_id` inside a magic-loop body (there is no current work item there) and a kernel that creates an array inside the body, which the device lifts to a host parameter and the interpreter rebuilds per work item.
- Kernel return values travel as *parameters*, not as a C return value: a launch is N work items, so the translator gives every returned position a slot (a one-element buffer for a value, the array object itself for an array) plus one shared claim word, and the first work item to reach a `return` claims the result with an atomic compare-and-swap. The winning site records its own shape, so different `return` statements may return different arities and types; a bare `return` yields None, and the `python` backend mirrors "first non-None result wins". Read the slots back on the host, and deliver an async result in the future's completion callback — never before launch completion. A value-returning `return` after the magic loop is refused *unless* the value is a launch-wide slot -- a carried scalar or a kernel argument -- because then every work item computes the same answer (see `_return_is_shared`).
- Outer-scope variables are parameterized, never inlined (`FunctionTranslator._bind_outer_variables`): a free variable or module global the body reads becomes a plain device parameter, refreshed every call so a changed value is visible; one declared `nonlocal`/`global` becomes `T*` with every use dereferenced and the final value written back to its cell / the module globals after the call. A helper called from a kernel gets the same parameters and the call site forwards them. Rebinding an outer array is refused; writing its elements is fine and reads back through the normal `KernelFlags` analysis.
- **A kernel body is three regions, and each runs a different number of times.** The magic loop (`for i in range(arr.shape[0])`, `enumerate(arr)`, `np.ndindex`/`np.ndenumerate`) is what divides them: statements **above** it and **below** the last one run once on the host (see the three-host-regions rule), and the loop body is emitted **once per work item**. A value `return` after the last loop is therefore allowed exactly when `_return_is_shared` says the value is launch-wide; an array return stays allowed because every work item names the same object. The magic loop itself does not survive as a loop: `for i in range(arr.shape[0])` becomes one work item per `i`, with the index expressed through `blockIdx`/`blockDim`/`threadIdx`, plus the bounds guard `if (i >= extent) return;`.
- Statements above the magic loop whose right-hand side only builds data (`np.zeros`, `np.full`, `np.arange`, `*_like`, `np.float32(...)`) are executed by the interpreter, not translated: the object is built on the host, travels as a parameter, and is handed back as the very same object when the body returns it. **A plain assignment above the loop that a creation reads is lifted and run by the host too**, so `n = 5; arr = np.zeros(n)` works: the host evaluates the assignments feeding the creation, in body order, before the launch. Only the *creation* travels to the device as a parameter -- the lifted plain assignments stay in the host namespace alone, because the work items compute them themselves and shipping them would add arguments nothing reads. Everything lifted this way is **still emitted as device code as well**; the host evaluation is an extra, not a replacement. The dependency set is closed to a fixed point (`a = 2; b = a * 2; c = np.zeros(b)` lifts all three), and only right-hand sides the host can genuinely run are lifted -- a literal, a name, attribute access, arithmetic, a subscript, a tuple. A **call** is not, because it may name a device helper whose body the host cannot run; `n = int(x.shape[0])` feeding a creation is therefore refused with `'arr' cannot be created here: ... could not be evaluated on the host; build it from values that exist at call time`, and `n = x.shape[0]` is the spelling that works. The creation's other sources are the kernel's arguments, the receiver, a module global or closure cell, and an *earlier* creation. Below the magic loop a creation runs once per work item, so it cannot be a host object: when its shape is a compile-time constant it is emitted as a **private C array** (`FunctionTranslator._emit_private_array`, initialised to match `zeros`/`ones`/`full`/`empty`, indexed like any array through a constant `_shape_var`), and a runtime extent is refused with a message rather than silently shared between work items. Keep the recognition list (`_HOST_CREATION_FUNCTIONS`) and the host-side evaluation (`_host_created_values` in `decorator.py`, which shares `_is_creation_shape`/`_is_host_evaluable` with the translator) in sync -- a constructor the translator accepts but the host cannot evaluate becomes a hard error.
- `bool` is not portable as a kernel parameter (OpenCL refuses a `_Bool` kernel argument, and the CUDA/HIP binding tables have no entry). It travels as a `uchar` with the host converting the argument, and a bool return slot is rebuilt as a python bool. `char` slots also use an unsigned byte, because OpenCL binds `char` to `ctypes.c_char` (|S1), which is not an integer array at all.
- `print()` inside a kernel is translated into device `printf` (`FunctionTranslator._emit_print`) on OpenCL and CUDA. A whole line must be **one** printf call site: every device call site owns an output buffer and the buffers are drained per call site, so a line split over several printf calls comes back interleaved with other work items. That is why a bool argument branches the line (one printf per `True`/`False`) and a real argument expands it per digit budget into a `switch` of literal formats — OpenCL rejects a computed format string, so `%.*f`/`%.*e` cannot be emitted. Keep the leaf count bounded by `PRINT_MAX_LINES`.
- `print()` is **deliberately rejected on HIP**. Do not try to "make it work" by experimenting with HIP printf kernels: on the tested ROCm 7.2 Windows machine, launching kernels that carry those printf call sites makes the AMD driver drop the device and Windows performs a display-driver reset (the machine has to be recovered). The OpenCL and CUDA paths are verified; treat the HIP rejection as the final behaviour.
- HIP reuses CUDA code generation, so `FunctionTranslator.backend` is `"cuda"` for a hip kernel. Anything that depends on the **runtime** rather than the generated syntax must read `FunctionTranslator.launch_backend` (passed from `PyKernel._compile` as the real backend), which is how the HIP print rejection above is implemented. Do not test `self.backend == "hip"` — it is never true.
- Floats print in python's shortest round-trip form, and the digit count is chosen on the device (`_print_real_selector`) because it is a per-value property. `PRINT_REAL_DIGITS`, `PRINT_REAL_SCI_HI`/`_LO` and `PRINT_REAL_PLAIN_MAX` encode numpy `str()` (float32) and python `repr()` (double) notation; do not collapse this back to one fixed `%g` precision.
- fp16 arguments are unsupported on CUDA/HIP; use float32.
- `math.trunc(v)` cannot work on the **interpreter** backend: it runs the body unchanged, so the call reaches `math.trunc` with the numpy scalar that `x[i]` is, and numpy's `float32` has no `__trunc__` (`__floor__`/`__ceil__` exist, which is why `floor`/`ceil` are fine). The GPU backends translate it normally, and `np.trunc(x[i])` and pygf's `trunc` work on all four. Fixing it would mean handing array elements to the interpreter as python floats, which would change far more than this.
- `mul24`/`mad24` are only defined for 24-bit inputs, and the backends genuinely differ outside that range — OpenCL emits the truncating hardware instruction while CUDA/HIP have none and fall back to a plain multiply (`device_builtins.py` says so). Measured: `mul24(1 << 24, 2)` is `33554432` on CUDA/HIP and on the host, and `0` on OpenCL. That is conforming, since OpenCL leaves the result undefined there, but a kernel that passes a wider value gets a different answer per backend with no diagnostic. Within 24 bits all four backends and the host agree.

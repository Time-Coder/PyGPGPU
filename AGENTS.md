# AGENTS.md

PyGPGPU runs Python functions as GPU kernels on OpenCL (default), CUDA, and HIP, and can also run them serially in the interpreter through the `python` backend. Pure Python + ctypes, Python >= 3.7, packaged with setuptools. `README.md` is the English version (shown first on GitHub); `README.zh-CN.md` holds the Chinese version and the two link to each other at the top — when editing user-facing docs, keep both in sync.

## Language policy: English only (hard rule)

- **All comments, docstrings, error messages, log/UI text, and every other string in code must be written in English. Never generate Chinese (CJK) characters** in `.py` / `.cl` / `.cu` / `.hip` sources, generated stubs and templates (`*.pyi`, `*.pyi.in`), `examples/`, or any documentation file.
- The **only** permitted Chinese files are `README.zh-CN.md` mirrors of an English `README.md`, in any directory (currently two: repo root and `examples/`). When user-facing docs change, keep the matching mirror in sync. Nothing else may be added in Chinese, and no code, script, or tool may emit Chinese text.
- One narrow exception, and do not extend it: the native-form author name in `pyproject.toml`'s `authors` table, kept alongside the ASCII `Binghui Wang` entry used everywhere else. Machine-readable packaging metadata is the only place CJK is allowed; the ASCII form is canonical for all prose, code, and display.
- If you find Chinese in a file you are touching, translate it to English as part of that edit rather than copying the style.
- Spot check before finishing a task: search the tree for CJK codepoints (`rg -n '[\p{Han}]' --glob '!README.zh-CN.md'`) — the only acceptable hits are the two `README.zh-CN.md` mirrors and the native-form author name in `pyproject.toml`. Language bars link with the word `[Chinese]`, never CJK, so no other file needs an exemption.
- This rule is self-referential: AGENTS.md itself contains no CJK, and neither should any file you add.

## Setup and verification

- `pip install -e ".[dev]"` (dev dependencies: pytest, ruff, ty). No CI and no pre-commit hook; the feature tests live in `tests/` and run with `python -m pytest tests/ -q`. The whole-repo check is `python check.py` (runs `ruff check --fix` then `ty check` against the config in `pyproject.toml`).
- Fast checks without a GPU: `python -m compileall -q pygpgpu` and `python -c "from pygpgpu.kernel import kernel"`.
- The end-to-end smoke tests are the numbered scripts in `examples/` (each is standalone: `python examples/01_basic_kernel.py`; no backend specified means probe `cuda -> hip -> opencl`). `examples/06_handwritten_kernels.py` covers the `.cl` import hook, struct parameters and static read/write analysis; `examples/09_reduction.py` covers atomics, local memory and tree reductions.
- `tests/conftest.py` parameterizes every test over the `python` backend plus whichever device backends this machine has, and provides the `runner(kernel, *args)` fixture that brackets the current backend. Write a test once and it covers every backend; use the `gpu_backend` fixture for tests that need a real device.
- Backend packages initialize their runtime eagerly: `import pygpgpu.cuda` needs `nvcuda.dll`; `import pygpgpu.hip` needs `amdhip64.dll` and raises when it is missing. Keep smoke scripts backend-specific instead of importing all three.
- HIP compiles by spawning ROCm's `clang.exe` (hipRTC is unusable on the tested ROCm 7.2 Windows). Set `PYGPGPU_HIP_INCLUDES` (`os.pathsep`-separated) when MSVC/Windows SDK headers are not auto-discovered.

## Layout and ownership

- `pygpgpu/kernel/`: `@kernel` decorator (`decorator.py`), Python-to-device AST translator (`translator.py`), and the device builtins (`builtins.py`). Backend-neutral except that HIP reuses CUDA generation. `python_backend.py` is the interpreter backend: it translates nothing and executes the body serially, so it is not a fourth code generator — keep it that way (no AST translation there, only the source scan that tells a magic loop from a gid-style body).
- The builtins are four files with one job each: `builtins.py` holds *only* the dual-sided functions a user may call, `builtin_registry.py` maps name <-> object for the translator, `device_builtins.py` holds how each name is emitted per backend, and `host_runtime.py` holds what the host bodies need (the per-launch frame and the flat read-modify-write). Do not add infrastructure to `builtins.py`. There is no `gpu` namespace: every builtin is exported from the `pygpgpu` top level, so an editor completes `pygpgpu.` and a type checker sees the real signature.
- A builtin call is recognized by the *object the callee resolves to* (`builtin_registry.builtin_name_of`), never by the spelling of the name, so a user's own `def dot(...)` stays an ordinary device helper while `from pygpgpu import dot`, `pygpgpu.dot(...)` and `from pygpgpu.kernel.builtins import dot` all translate as the builtin; `FunctionTranslator._builtin_call_name` is the single place that decides this. Add a builtin by defining it in `builtins.py`, listing it in `builtins.__all__`, and adding its device mapping to `device_builtins.py`; `tests/test_builtins.py` fails if the three disagree.
- **One object per builtin name, and the host and the device must agree on what it accepts.** A name pygf also publishes is *pygf's object*, re-exported by `pygpgpu/vec_types/funcs.py` — never a second implementation, because a kernel that imported one copy would translate as an ordinary device helper (whose body has no device meaning), and two host contracts for one name would make a kernel mean different things per backend. This is why `dot` is **vector-only on both sides**: pygf refuses a scalar pair, so the device refuses it too and points at `a * b`, rather than reducing it to a multiply the way it once did.
- **Eight builtins are OpenCL-only and their host bodies live here: `select`, `isordered`, `isunordered`, `abs_diff`, `hadd`, `rhadd`, `mul24`, `mad24`.** They *are* vector operations — every one of them is component-wise — so "pygf has no such operation" is not the reason. Two other reasons are: (1) pygf is a **GLSL-shaped** function set whose spellings exist so a transpiler can map them without a rename table, and none of these eight has a GLSL spelling at all, so hosting them there would mean either adding OpenCL names to that set or inventing names for it; (2) `mul24`/`mad24` are named after a hardware instruction rather than a mathematical operation, and OpenCL leaves them undefined outside 24-bit inputs — see the scope note below. Where a host body lives is independent of whether something is a builtin: all eight keep a `device_builtins` emission and must stay dual-sided. They are still defined in `funcs.py` beside the pygf re-exports; splitting them into their own module would make the boundary visible but changes nothing semantically.
- Vector types live in `_vec_registry()` (the OpenCL driver's classes). A 3-component vector is padded to 16 bytes *on OpenCL only*: the host (`pygf`) and CUDA/HIP store it in three components. The boundary is `pygpgpu/vec_types/layout.py` — `pack(value, backend)` returns the backend's layout plus a write-back callable, recursively over vector instances, vector-dtype arrays, and `ctypes.Structure`s (including nested ones and arrays of vectors); the host-visible form never changes, and the conversion is a no-op for CUDA/HIP and for widths other than three. Do not re-derive a vec3 layout anywhere else; `HIPInfo.vec_types` must keep using CUDA's table, because HIP's ABI is CUDA's, not OpenCL's. Every place that counts or names components goes through `_vec_components` / `_vec_field_names`, or the padding leaks into a constructor arity, a swizzle or a print.
- A vector-dtype ndarray would expose `np.void` records on the host, where `.x` does not exist and a vector cannot be assigned. That is **pygf's** job, not this repo's: `pygf/vector_array.py` provides the `VectorArray` view, patches the numpy constructors so a vector-dtype array is born as that view, and makes `np.array`/`np.asarray` read a sequence of vector instances as an array of vectors (numpy would otherwise flatten each one into a wider numeric array, which is what made `np.array([float3(...), float3(...)])` a `(2, 3)` float64 matrix). `pygf.register_vector_type` is how the types this repo adds — the 8/16-wide widths and the char/uchar/short families — join that registry: `pygpgpu/vec_types/__init__.py` registers them at import, and an unregistered type comes back as plain records. Do not reintroduce a copy of the patch here; the numpy surface for these types has one owner. Anything that inspects a value's *class name* to decide it is a vector must exclude `np.generic` first, because `np.uint8`'s class name collides with the registry's eight-component `uint8`.
- `np.ndindex` may take extents from an array dimension (`x.shape[0]`), a literal (`2, 3`), or a host-side integer argument (`self.image_height`, recorded as the `-2` marker in `work_size_dims`). A loop's index-name count must equal its domain rank, which is checked at launch: `np.ndindex(arr.shape)` with fewer names than `arr.ndim` would otherwise iterate a prefix of the axes and leave the rest constant.
- A structure is a **numpy record dtype**: `np.dtype([("i", "<i4"), ("f", "<f4")])` fully describes the layout, so `pygpgpu/kernel/structs.py` generates the device type from it (`register`/`struct_name`/`render_structures`, nested structures first) and a Python-level `np.ndarray` of that dtype is an array of the structure. Member access keeps numpy's spelling: `s["i"]` is emitted as C member access, and it works for vectors too (`v["x"]`), which is what makes `record["v"]["x"]` behave the same in the interpreter and on a device. Member assignment is routed through `_struct_member_access` in both `_visit_target` and the `_visit_assign` subscript branch, and it records the array in `atomic_targets` because the generated `(rows[i]).i = v` is not attributed to the array by the static read/write analysis.
- **A caller's `ctypes.Structure` class is a second entrance to the same mechanism**, not a separate one: `np.dtype(cls)` yields the same record a hand-written dtype would, so `structs.register_class` / `structure_dtype_of` route it through the identical code path — as an array, as a by-value argument, as a nested member, and as an object the body created. Three things this depends on: (1) a dtype cannot say whether it means a structure or a vector — `{float x; float y;}` compares *equal* to `float2` and hashes the same — so the only evidence is `isalignedstruct`, true for a record built from a ctypes class and false for every vector dtype this package ships; do not reintroduce a dtype-keyed registry keyed on equality, it cannot work; (2) a vector type is itself a `ctypes.Structure`, so `structure_dtype_of` excludes `_vec_registry()` and the pygf aliases before it can report a structure, and `pygf.vector_class_for_dtype` applies the same alignment test from the other side; (3) the parsed device type is a *different* class from the caller's, so every backend converts an instance through its bytes (`content_type.from_buffer_copy(bytes(value))`) instead of expecting `isinstance` — and the `python` backend does the mirror conversion in `as_host_array`, handing the body a record so `p["i"]` works.
- **`Ray(origin, direction)` builds a structure value.** A class call on a `ctypes.Structure` subclass is not object construction — the class is a layout, so the call becomes an aggregate initialiser (`_emit_structure_constructor`). The spelling is per backend: OpenCL C is C99 and names its members (`.origin = ...`), while CUDA/HIP compile as C++ where designated initialisers need C++20, so they fill every member **positionally in declaration order**, spelling an omitted one as the zero of its type (`_zero_value`). Every other class stays refused, because there is nothing on a device to instantiate. A member-name subscript (`s["i"]`) is also installed on a declared class (`structs._add_subscript_access`) so the interpreter, which runs the body unchanged, reads a member exactly as a device body does — and `pygf`'s vector `__getitem__` accepts a component name (`v["x"]`) for the same reason. Both are gated on the class not already having a subscript, and `register_class` must keep skipping vector types, or it would replace their positional `v[0]`.
- **Structure typedefs belong to the whole source, not to one function.** A helper's signature can name a structure (`def ray_color(ray: Ray)`), so the type block is collected from `translator.structure_dtypes()` plus each `device_cache` entry's `structs` and emitted **once**, ahead of every device function and the kernel (`PyKernel._compile`). Emitting it per function defines the same struct twice, which C++ rejects; emitting it nowhere fails only when the helper is involved, which is why the ray-tracing example compiled its own kernel and then failed on the helper.
- **`value.method(args)` is a device call whose first argument is the value.** A method is an ordinary python function whose first parameter is the receiver, which is what `self` already is in a device helper, so `_emit_method_on_value` translates it as `_emit_device_call(attr, func, [receiver] + args)` — no new machinery, and the body then reads `self.origin` exactly as a structure-typed parameter would. The receiver may be a parameter, a local, a constructed value, or a member of one (`a.b.method()`), because the branch is keyed on the receiver being a *value* rather than a Name that resolves to a module or a class. The class has to be reachable, which is why only a `ctypes.Structure` subclass and a vector type qualify: two classes with one layout share a dtype, so a bare record dtype cannot say whose methods to compile, and the error says so. A `self.`-prefixed call still goes through the kernel-method path first, and `module.function(...)` is now gated on `inspect.ismodule` so a global *object* carrying the attribute is not mistaken for a module.
- **A device helper resolves names in its own module first, then the caller's.** `_helper_globals` builds that resolver: a helper is an ordinary function, so a name its body reads is the one its own module defines — `ray.py`'s `hit_sphere` sees the `dot` that `ray.py` imported — while falling back to the kernel's resolver keeps outer-scope variables working (a helper reading a global of the kernel's module still has it forwarded as a parameter at the call site). Resolving everything against the kernel's globals only worked while helpers lived beside the kernel. The namespace the name came from travels in the outer-variable entry as `scope`, because the host has to read the *same* namespace at launch: `_read_outer` prefers it, and without it a helper's own-module global arrived as `None`.
- **A scalar call has three acceptable spellings — python's builtin, `math.*` and `np.*` — and all three translate when the device has a form.** `abs`/`min`/`max`/`round`/`pow`/`float`/`int`/`len` go through `_emit_builtin`; `math.*` and `np.*` share `_emit_math_call`, with `np.minimum`/`maximum`/`square`/`reciprocal`/`abs`/`round` and the `power`/`arctan2` aliases handled in `_emit_numpy_elementwise`. Three things there are load-bearing: (1) `_math_device_name` picks the device spelling, because CUDA has no `degrees`/`radians` intrinsic (they become a multiply) and its predicates take no `f` suffix; (2) a function whose *python* result type differs from its argument type is cast on the **result**, never the argument — `math.floor`/`ceil`/`trunc` return an int, and casting the argument made the device see `floor((int)x)`, which CUDA rejects as ambiguous and which answered `ceil(2.1)` = 2; (3) `isnan`/`isinf`/`isfinite` take a float and answer 0/1, and casting that float to the int answer was the same bug. `tests/test_kernel_scalar_calls.py` covers every spelling on every backend.
- **pygf's alias types carry a meaning and its arithmetic keeps it.** `point3f`, `vector3f`, `normal3f`, `color3f` and `texCoord3f` are a `float3` with the same dtype, so the result class is the only record of whether a value is a position or an offset; pygf decides that in `genType._bin_op_type` (and reclasses in `genMat._op`), and nothing here has to know. It reaches PyGPGPU in one place only: the `python` backend runs a kernel body's host arithmetic unchanged, so a body doing `center - origin` gets a `vector3f` and a constructed `Ray` keeps its positions. The device side is unaffected -- the two classes share a dtype, so a translated argument is a `float3` either way, and `infer_ctype` reads the dtype rather than the class name.
- **An arbitrary python object is accepted anywhere a structure is, and the structure is synthesized from what the body reads.** `objects.py` runs before `infer_ctype` in `_invoke_inner`: it scans the kernel and the helpers it calls (`_scan_function`) for the attributes each object parameter's reader touches, builds a `ctypes.Structure` from those members (types taken from the values the caller passed), and hands the translator a real structure so typedefs, member access, layout and packing all work unchanged. The scan resolves `p.x`, local aliases, `helper(p)` forwarding, `p.method()` (the method is copied onto the synthesized class), one level of nested objects (`p.inner.a` becomes its own path and a nested structure), and a list of objects of one class (`items[j].x` and `for e in items` make the list a record array of the element structure; mixed classes are refused, because a device loop cannot dispatch per element). Two objects of one class merge into one structure when their member types promote (`int` widens to `float`); they stay two structures when an instance lacks a member or the types do not mix. The scan is deliberately narrow — everything it cannot answer (a nested non-object, an array member, `getattr`, an object nothing reads, an empty or mixed list) is refused with a message naming the shape, never guessed at.
- **A member write on an object argument travels back.** By value the device would write its own copy, so a written object (`acc.total = ...`) travels as a **one-element record array** instead: a pointer, whose stores land in device memory the host reads back. `translator.atomic_targets` is force-marked for the array (the static analysis sees a member expression, not a subscript, and would otherwise skip the read-back), and `ObjectBinding.write_back` then `setattr`s the final values onto the caller's object after the launch. Writes to a property or outside `__slots__` are refused at scan time (there is nowhere for the value to land), and writes to a list element are refused (the element array is rebuilt per launch from the caller's list).
- **A member that is a list of objects becomes a fixed-length array member**, not a separate argument: `scene.hittables` is a `struct Scene { Hitables[N]; ... }`, with `N` and the element structure taken from the caller's list at launch. `for h in scene.hittables:` translates into an indexed loop with `h` a value copy of the current element (`_emit_element_loop`), and `len(scene.hittables)` reads the compile-time `N` back out of the member's dtype. The scan reaches the member list through a method chain too (`ray_color` -> `hit` -> `self.hittables`), because a method body is walked by the same `_scan_function` bound to the receiver. A list nested inside a list is refused.
- **A structure constructor accepts keywords as well as positions.** `Ray(origin=p, direction=d)` is rewritten by `_visit_structure_constructor_call` before the generic keyword reordering, which only knows plain functions. A keyword names a member exactly as python's ctypes spelling does, an unknown name lists the available members, the same member supplied twice is refused, and omitted members are zeroed. Positional arguments still fill declaration order.
- **`math.inf` is `(1.0f / 0.0f)`, never the `INFINITY` macro.** NVRTC's default headers do not define `INFINITY`, so a kernel using it failed CUDA compilation with "identifier INFINITY is undefined"; a literal is the same value on every backend and needs no header.
- **CUDA has no unary minus on a vector type.** `-v` is expanded per component (`_vec_componentwise("-", ...)`), like every other vector operation there; emitting `(-v)` made CUDA reject it with "no operator \"-\" matches these operands".
- **A method that writes its receiver's members takes the receiver by address.** A by-value structure is a copy, so `self.normal = ...` inside `HitRecord.set_face_normal` landed in the callee's local and never reached the caller's record -- the GPU drew a uniformly grey ball while the interpreter, which runs the method unchanged, was correct. `writes_receiver` decides this per method, the call site passes `&(value)`, and a receiver already travelling as a record array is handed over as it is. The body spells the access `(self[0]).x`, which is `(*self).x` for a pointer; a `(&x)` receiver reads as `(&x)->x`.
- **A `bool` structure member is stored as a byte, so a value assigned to it must be converted boolean.** `front_face = dot(...)` assigned the raw float, `unsigned char` truncated `0.99` to `0`, and the branch reading it went the wrong way -- the sphere lost its blue channel and came out grey. `_structure_member_value` and the member-store path in `_visit_assign` both emit `((value) != 0)` when the target's *layout* type is bool, which `_member_is_bool` / `_target_is_bool_member` read from the dtype (a member's device type is `uchar`, so the device-type name alone cannot say this).
- **A structure value takes no operator at all.** `_is_structure_operand` refuses `+ - * / % ** //` in `_visit_binop` and every comparison in `_visit_compare`, before the vector dispatch, and names the two escapes: operate on the members, or move the computation into a host method. Before this, `s * s` fell through to a per-component **scalar** multiply (`make_float3((v.x * q), ...)`) -- a C++ error that only surfaced when the value happened to compile, so the language never defined what it computed. The one exception is a quaternion, handled before this check.
- **Quaternion structures and their arithmetic live in one real header, `pygpgpu/kernel/include/quat.h`.** pygf gives a quaternion three meanings the C operators cannot express: `q * q` composes rotations, `q * v` rotates a vector, `conjugate(q)` flips the axis. All of it -- the two structures and every operation -- is plain C in that file, so a generated source that includes it declares nothing itself. The types carry **fixed** names (`quatf` / `quatd`) rather than the content hash other structures get, which is what makes that possible: a hash cannot be spelled in advance. `structs.struct_name` returns the fixed name for a quaternion and `render_structures` skips it, so the typedef block never declares it twice. A source defines `QUAT_QUAL` (empty, or `__device__` on CUDA/HIP) plus `QUAT_NEED_FLOAT` / `QUAT_NEED_DOUBLE` for the widths in use, then includes the header once as `#include "include/quat.h"`. The guards are load-bearing: a `double` variable does not compile on an OpenCL device without `cl_khr_fp64`, so an unused block must be absent, not merely unused. **A float and a double operand mix and the result is always the double form** (`quatf * quatd` is a `quatd`, `quatf * double3` a `double3`, `quatd * float3` a `double3`), which is pygf's rule; the header spells each mixed combination as `<left>_<op>_<right>`, and that block needs **both** macros. `#include` is expanded by `cpreprocessor.macros_expand` **before** the backend compiler runs, so the header is plain text folded into the generated file; a copy still goes into `<cache>/pykernels/include/` because a quoted include resolves relative to the including file, and `package-data` ships `kernel/include/*.h`. The placement is **per cache, not per user**, so a cache stays self-contained. The caller passes the **cache directory** to `include_line`, which places the file -- do not pre-append `include/` at the call site or the folder nests twice. Two cross-dialect details: OpenCL has no `sqrtf`, only `sqrt` (a `sqrtf` there failed to compile), and the mixed helpers need `QUAT_QUAL` too. The bodies mirror `genQuat._op` line for line; a rotation is `q * v * conj(q) / |q|`, normalised by **q** magnitude rather than the product; and `_add_subscript_access` walks the whole MRO before installing a member-name subscript, because `quatf` inherits `__getitem__` from `genType` and shadowing it broke `conjugate(q)` inside pygf itself.
- **`zeros_per_group` and `zeros_per_block` are one function under two names, and the one-object-per-name rule permits that because there is still exactly one implementation.** A CUDA reader looks for "block" and an OpenCL reader for "group", so refusing one spelling would make half the readers hunt for an alias; both are published, and `zeros_per_block = zeros_per_group` makes them the same object, so a kernel means the same thing however it spells the call. Do not give either name its own body: that is what the rule forbids, and `builtin_registry` indexes by object identity, so two bodies would also make the two names translate as different builtins.
- `pygpgpu/{opencl,cuda,hip}/oop/`: parallel Device/Context/Buffer/Program/Kernel APIs. The three stacks are intentionally similar but not shared; a semantic change usually needs mirrored edits in all three.
- `pygpgpu/cparser/`: the active parse path is `cpreprocessor.py` + `ts_parser.py` (tree-sitter mixin used by all backends). `cparser.py`, `csyntaxtree.py`, `ctokens.py`, and `ShaderBuiltins.py` are legacy and not imported at runtime. `pcpp/` is vendored; avoid patching it.
- `climport` / `cuimport` / `hipimport`: meta-path finders that let `.cl` / `.cu` / `.hip` files be imported like modules. Importing a backend package installs its hook; resolution walks `sys.path`.
- `pygpgpu/numpy/` is `gnp`: a device-resident `np.ndarray` subclass shared by all backends through the context/stream interfaces.

## Repo-specific behavior to preserve

- `(global, local)` work sizes use total-work-item semantics on every backend; CUDA/HIP grid dimensions are derived as `global // local`. Do not reinterpret `global` as a block count.
- Automatic work sizes are chosen in `utils.py` (`detect_work_size` / `local_size_for_global`): the local size comes from the extents (or their divisors) and is clamped to the device's real limits, preferring warp-aligned groups. The derived `global` is intentionally **not** required to equal the array length: when a bounds guard is guaranteed (`@kernel` always emits one) the global may be rounded up to a multiple of the local, which keeps work groups efficient for awkward extents such as prime lengths. Do not "fix" this rounding back to exact equality.
- Handwritten kernels must clamp themselves against the real element count passed as an argument. `get_global_size(dim)` reports the (rounded) launch size, not the buffer length, so it is not a valid bound; see `examples/vecadd.cl`.
- A gid-style kernel (`get_global_id`) has no loop for the automatic work size to read a domain from, so it must declare one: `work_size(x)` at the top of the body (host-side only, erased by the translator, contributes all of `x`'s dimensions) or a `k[(total, local)]` bracket. Without either, the launch raises instead of falling back to a buffer-shape guess: that guess used to silently pick a 1-work-item grid for a 100000-element reduction and produce a wrong answer.
- **Shared (work-group) memory is `buf = zeros_per_group(shape, dtype)` (or `zeros_per_block`, the same function), indexed by the group first: `buf[blockIdx][...]`.** The arguments are `np.zeros`'s own and in its own order -- **shape first, dtype second** (`zeros_per_group(256, np.int32)`, `zeros_per_group((64, 64), np.float32)`) -- and the shape may be an int or a tuple of them, so a multidimensional buffer indexes as `buf[blockIdx][i, j]` or, equivalently, as `buf[blockIdx][i][j]`: a single subscript consumes one axis and hands back a slice carrying the remaining axes plus the offset so far, which is how the nested spelling reaches the same element. The shape must be a **compile-time constant** (a literal int or tuple; a module constant is refused too), because the buffer is a fixed-size `__shared__` array on CUDA/HIP and one `__local` parameter on OpenCL, so a launch-time size cannot declare it.  The value stands for **every group's slice at once**, so the model is honest on both sides. On the **host** it really is a mapping -- block id to that group's array -- which is why the first subscript is required; on the **device** it produces no index arithmetic at all: the emitted code is a plain `__shared__` array (CUDA/HIP) or `__local` parameter (OpenCL), which the hardware already gives each group privately, so `buf[blockIdx][j]` folds to `buf[j]`. `_visit_shared_slice` therefore **validates** the group subscript rather than computing one (it must be `blockIdx` or `get_group_id(d)`, or a local assigned from one), and any other index is refused: emitting that as an offset would read the **next** group's copy, which is exactly the memory a work item must never touch. Two consequences are load-bearing: `_is_local_buffer` accepts both the buffer and its slice (`bins[blockIdx]`), because an atomic call passes the slice and answering False there made the OpenCL cast say `__global`, which the compiler rejects as a change of address space; and a bare `buf` is refused, since naming the whole mapping has no device meaning. A shape built from a name is refused for the same reason: `zeros_per_group(GROUP, np.float32)` is refused with "zeros_per_group() shape must be a constant positive integer or a tuple of them" even when `GROUP` is a module constant (which is why `examples/09_reduction.py` mirrors its `GROUP` by hand). The dtype must be a numpy one (`np.int32`, or the string `"int32"`); `half` is refused. A `barrier()` is required between the write phase and the read phase -- without it a work item reads a slot another group member has not written yet. **The interpreter backend refuses it outright**: it runs the body serially and `barrier()` is a no-op there, so an algorithm counting into shared memory would quietly return a different number instead of failing. Use a device backend, or sum straight into an array argument with `atomic_add` (integers only -- atomic float is not implemented on OpenCL here, so scale to integers or use the shared-memory tree, which is what the reduction example shows).
- **CUDA's index names are `int3` values, not calls: `blockIdx`, `threadIdx`, `blockDim`, `gridDim`.** A CUDA programmer reaches for `blockIdx.x`, and a ported kernel should not have to be rewritten, so each is published as a three-axis vector whose components are the same numbers the OpenCL spellings give per axis (`blockIdx.x` is `get_group_id(0)`, `threadIdx.x` is `get_local_id(0)`, `blockDim.x` is `get_local_size(0)`, `gridDim.x` is `get_num_groups(0)`). They are **values**, so no parentheses: `buf[blockIdx][j]` and `blk = blockIdx.x`. A value cannot hold a per-launch number, so on the host these are lazy `_IndexVector` objects reading the current launch frame; the device does not see that class at all -- `_visit_name` resolves the **name** through `INDEX_VECTOR_BUILTINS` (CUDA) or `INDEX_VECTOR_OPENCL` and emits the vector directly, so the two sides cannot disagree. One detail is load-bearing: `_IndexVector.__hash__` must not evaluate the readers, because the object is a registry key (`BUILTIN_NAMES_BY_FUNCTION`) and hashing it during import would ask for a launch frame that does not exist yet.
- `@kernel` specialization is per backend + device + argument type signature, compiled at first call rather than decoration. Kernels need retrievable Python source: define them in real `.py` files, not stdin/`exec` strings (`inspect.getsource`).
- Helper functions called from a kernel need no decorator and no annotations: `_emit_device_call` translates them into device functions and monomorphizes per call-site argument types, recursively. Emission order must be dependency order (`_dependency_order` in `decorator.py`) because C requires a callee before its caller and the cache fills depth-first. A helper defined in `python -c`/stdin has a `<string>` filename and yields an invalid C identifier, so keep helpers in real `.py` files.
- All three backends can be used in one process, and the same `PyKernel` object caches one specialization per backend + device + signature. Keep that working: do not add process-wide backend state (Taichi-style `init(arch=...)` global config), and keep backend package imports lazy so importing `pygpgpu` still needs no GPU runtime. The `python` backend takes part in the same bracket dispatch but caches nothing (there is nothing to specialize) and is never probed as a default, so a machine without a GPU keeps raising instead of silently falling back to the interpreter.
- The `python` backend's launch semantics must stay in step with the GPU ones: a magic-loop body runs once as written, a gid-style body runs once per work item of its `work_size(...)` domain or `(total, local)` bracket, and each builtin resolves through the thread-local frame in `host_runtime.py` so concurrent launches never share a work item. That frame holds only the launch shape and the current work item; the operations themselves are the bodies in `builtins.py`.
- Static read/write analysis (`KernelFlags` in `constants.py`, implemented in `ts_parser.py`) decides which arguments are uploaded/downloaded. Do not defeat it when adding argument handling. A written buffer is always *also* uploaded: the download copies the whole buffer back, so a buffer that was never uploaded would replace every element the kernel did not write with a fresh device buffer's zeros, losing what the caller had. An argument explicitly declared `write_only` is the only exception.
- `arr[i] op= value` becomes a device atomic operation whenever the translator cannot prove the element is private to the work item (`FunctionTranslator._augassign_is_race_free`). The proof is deliberately narrow: the subscript must be built from exactly the magic loop's index variables, each once. Anything else — a data-driven index like `bins[image[i]] += 1`, a partial tuple, an arithmetic index — is racy, and a plain read-modify-write there silently loses contributions (a histogram written that way counted 256 of 4096 pixels per channel). Only operators with an atomic counterpart are accepted (`+=`, `-=`, `&=`, `|=`, `^=`); a racy `*=`/`/=`/`**=` or a racy float accumulation raises a `SyntaxError` telling the user to use an integer buffer or a reduction, because atomic float is not implemented on OpenCL here.
- An outer scalar (`nonlocal`/`global`) is **always** racy, since every work item shares the one location, so `counter += 1` on it is always emitted as an atomic and the result is written back after the call. Two things this depends on: outer scalars are stored as `name[0]` rather than `(*name)` (`_visit_target`), because the read/write analysis only recognizes the subscript form as a write and otherwise leaves the buffer un-read-back — the host then kept its initial value; and `atomic_add(counter, 0, 1)` is **refused** with a message pointing at `counter += 1`, because atomic operations index an array. A 1-element array remains the spelling that works for an explicit atomic on a caller-owned scalar.
- Importing `pygpgpu` monkey-patches `numpy.array` process-wide to support nested `ctypes.Structure` values. Keep that behavior unless the change is deliberate.
- Caches live beside the source (`__clcache__`, `__cucache__`, `__hipcache__`; generated `@kernel` sources under `.../pykernels`) and invalidate by mtime/source hash. Delete the relevant cache when debugging stale generated code.
- Handwritten-kernel `.pyi` stubs are regenerated next to the source on import; `examples/vecadd.pyi` comes from `examples/vecadd.cl`. Edit the kernel/parser, not the generated stub.
- Regenerate the vector-type stubs with `python -m pygpgpu.vec_types.helper`; templates are `genVecN.pyi.in`.

## Known scope limits

- `@kernel` does not support strings/lists/dicts, recursion, or dynamic multi-dimensional indexing; unsupported syntax raises a plain `SyntaxError` positioned at the offending line. These limits belong to the GPU translator: the `python` backend runs the body as-is and accepts such code, except `zeros_per_group` (no serial equivalent) and `get_global_id` inside a magic-loop body (no current work item).
- Kernel return values travel as *parameters*, not as a C return value: a launch is N work items, so the translator gives every returned position a slot (a one-element buffer for a value, the array object itself for an array) plus one shared claim word, and the first work item to reach a `return` claims the result with an atomic compare-and-swap. The winning site records its own shape, so different `return` statements may return different arities and types; a bare `return` yields None, and the `python` backend mirrors "first non-None result wins". Read the slots back on the host, and deliver an async result in the future's completion callback — never before launch completion. A value-returning `return` after the magic loop is refused: it would return one work item's local rather than the function's result.
- Outer-scope variables are parameterized, never inlined (`FunctionTranslator._bind_outer_variables`): a free variable or module global the body reads becomes a plain device parameter, refreshed every call so a changed value is visible; one declared `nonlocal`/`global` becomes `T*` with every use dereferenced and the final value written back to its cell / the module globals after the call. A helper called from a kernel gets the same parameters and the call site forwards them. Rebinding an outer array is refused; writing its elements is fine and reads back through the normal `KernelFlags` analysis.
- **A kernel body is three regions, and each runs a different number of times.** The magic loop (`for i in range(arr.shape[0])`, `enumerate(arr)`, `np.ndindex`/`np.ndenumerate`) is what divides them: statements **above** it are emitted once at the top of the kernel, the loop body is emitted **once per work item**, and statements **below** it are also emitted into every work item — not once for the function. The interpreter backend is the readable reference: it runs the body as written, so an `above` statement executes once, the loop body N times, and the `below` statements once (python's own semantics, since the function returns after the loop). On the device the `below` region therefore executes N times, which is why two things are refused there: a *value* `return` (`_visit_kernel_return` — it would hand back one work item's local rather than the function's result; an array return stays allowed because every work item names the same object) and a data **creation** (it would build N objects where python builds one). The magic loop itself does not survive as a loop: `for i in range(arr.shape[0])` becomes one work item per `i`, with the index expressed through `blockIdx`/`blockDim`/`threadIdx`, plus the bounds guard `if (i >= extent) return;`.
- Statements above the magic loop whose right-hand side only builds data (`np.zeros`, `np.full`, `np.arange`, `*_like`, `np.float32(...)`) are executed by the interpreter, not translated: the object is built on the host, travels as a parameter, and is handed back as the very same object when the body returns it. **A plain assignment above the loop that a creation reads is lifted and run by the host too**, so `n = 5; arr = np.zeros(n)` works: the host evaluates the assignments feeding the creation, in body order, before the launch. Only the *creation* travels to the device as a parameter -- the lifted plain assignments stay in the host namespace alone, because the work items compute them themselves and shipping them would add arguments nothing reads. Everything lifted this way is **still emitted as device code as well**; the host evaluation is an extra, not a replacement. The dependency set is closed to a fixed point (`a = 2; b = a * 2; c = np.zeros(b)` lifts all three), and only right-hand sides the host can genuinely run are lifted -- a literal, a name, attribute access, arithmetic, a subscript, a tuple. A **call** is not, because it may name a device helper whose body the host cannot run; `n = int(x.shape[0])` feeding a creation is therefore refused with `'arr' cannot be created here: ... could not be evaluated on the host; build it from values that exist at call time`, and `n = x.shape[0]` is the spelling that works. The creation's other sources are the kernel's arguments, the receiver, a module global or closure cell, and an *earlier* creation. Below the magic loop a creation runs once per work item, so it cannot be a host object: when its shape is a compile-time constant it is emitted as a **private C array** (`FunctionTranslator._emit_private_array`, initialised to match `zeros`/`ones`/`full`/`empty`, indexed like any array through a constant `_shape_var`), and a runtime extent is refused with a message rather than silently shared between work items. Keep the recognition list (`_HOST_CREATION_FUNCTIONS`) and the host-side evaluation (`_host_created_values` in `decorator.py`, which shares `_is_creation_shape`/`_is_host_evaluable` with the translator) in sync -- a constructor the translator accepts but the host cannot evaluate becomes a hard error.
- `bool` is not portable as a kernel parameter (OpenCL refuses a `_Bool` kernel argument, and the CUDA/HIP binding tables have no entry). It travels as a `uchar` with the host converting the argument, and a bool return slot is rebuilt as a python bool. `char` slots also use an unsigned byte, because OpenCL binds `char` to `ctypes.c_char` (|S1), which is not an integer array at all.
- `print()` inside a kernel is translated into device `printf` (`FunctionTranslator._emit_print`) on OpenCL and CUDA. A whole line must be **one** printf call site: every device call site owns an output buffer and the buffers are drained per call site, so a line split over several printf calls comes back interleaved with other work items. That is why a bool argument branches the line (one printf per `True`/`False`) and a real argument expands it per digit budget into a `switch` of literal formats — OpenCL rejects a computed format string, so `%.*f`/`%.*e` cannot be emitted. Keep the leaf count bounded by `PRINT_MAX_LINES`.
- `print()` is **deliberately rejected on HIP**. Do not try to "make it work" by experimenting with HIP printf kernels: on the tested ROCm 7.2 Windows machine, launching kernels that carry those printf call sites makes the AMD driver drop the device and Windows performs a display-driver reset (the machine has to be recovered). The OpenCL and CUDA paths are verified; treat the HIP rejection as the final behaviour.
- HIP reuses CUDA code generation, so `FunctionTranslator.backend` is `"cuda"` for a hip kernel. Anything that depends on the **runtime** rather than the generated syntax must read `FunctionTranslator.launch_backend` (passed from `PyKernel._compile` as the real backend), which is how the HIP print rejection above is implemented. Do not test `self.backend == "hip"` — it is never true.
- Floats print in python's shortest round-trip form, and the digit count is chosen on the device (`_print_real_selector`) because it is a per-value property. `PRINT_REAL_DIGITS`, `PRINT_REAL_SCI_HI`/`_LO` and `PRINT_REAL_PLAIN_MAX` encode numpy `str()` (float32) and python `repr()` (double) notation; do not collapse this back to one fixed `%g` precision.
- fp16 arguments are unsupported on CUDA/HIP; use float32.
- `math.trunc(v)` cannot work on the **interpreter** backend: it runs the body unchanged, so the call reaches `math.trunc` with the numpy scalar that `x[i]` is, and numpy's `float32` has no `__trunc__` (`__floor__`/`__ceil__` exist, which is why `floor`/`ceil` are fine). The GPU backends translate it normally, and `np.trunc(x[i])` and pygf's `trunc` work on all four. Fixing it would mean handing array elements to the interpreter as python floats, which would change far more than this.
- `mul24`/`mad24` are only defined for 24-bit inputs, and the backends genuinely differ outside that range — OpenCL emits the truncating hardware instruction while CUDA/HIP have none and fall back to a plain multiply (`device_builtins.py` says so). Measured: `mul24(1 << 24, 2)` is `33554432` on CUDA/HIP and on the host, and `0` on OpenCL. That is conforming, since OpenCL leaves the result undefined there, but a kernel that passes a wider value gets a different answer per backend with no diagnostic. Within 24 bits all four backends and the host agree.
